# Scenarios — samples/svelte-spa

Every scenario in `docs/samples/PLAN.md` §4, plus svelte-spa's own (§5.4 "beyond the catalog").
Verified against Bugsee staging app **`SSVELTE`** (`6a8ebe51d58badbb348fbec4`), type `javascript`,
subtype `svelte`. `pnpm verify` runs **104/104** on stock Chromium against the real staging collector,
measured green on **three consecutive runs** of this build against the CURRENT SDK — every one 104/104,
storm settle 83.5-85.9s, 97 admitted on every single run, S12 recovery on a clear channel every run.
(An earlier build of this sample measured 88/88 across eleven consecutive runs; the count moved because
the SDK substrate changed under it — session replay became ON BY DEFAULT and a `sendBeacon` interceptor
was added — and this round added the checks those changes call for.) That count is not a durable property of the sample and should not be quoted as one — an
earlier round claimed "86/86 clean" as a fact about the sample while five consecutive re-review sweeps
actually scored 84/86, 86/86, 84/86, 86/86, 86/86, i.e. roughly 60% green; the cause was this script's
own storm-settle budget, not the SDK, and is written up on the S4 storm / S1 flush / S12 rows. Re-run it
rather than trusting the number. No CORS/proxy workarounds are needed (the cross-cutting wire-contract defects in
`samples/FINDINGS.md` F-X6/F-X10 were already fixed on `main` before this sample was built). A
`src/bugsee-transport.ts` tee (an `HttpTransport` that forwards every SDK call to real staging
verbatim while recording a parsed copy locally, including a genuine unzip of each uploaded bundle)
backs every row marked **W** below that reads UPLOADED bundle content rather than just an in-app
callback log or a raw call count.

Depth key (PLAN §4 "Verification depth"): **L** = local (no throw, app behaved) · **W** = wire (the
right request left the process, inspected via Playwright) · **B** = backend (confirmed via MCP
`list_issues`/`get_issue`).

**The `SSVELTE-NN` keys below are re-derived, not durable.** Bugsee fingerprints an issue on the stack
frames' `file:line`, and in dev mode the frame URL is the vite-served module URL — so ANY edit to a
sample source file mints a NEW issue for every control whose throw site moved, and vite's HMR
cache-buster re-mints them again even when nothing moved (measured directly: a sweep run while the dev
server had HMR-invalidated modules produced a full parallel set of issues whose frames read
`ScenarioPage.svelte?t=1787776468813:256:34`, while a run against a freshly restarted server produced
`ScenarioPage.svelte:256:34` and re-used the earlier fingerprints). Every key in this file was
re-derived from `list_issues` after the final sweep, against a dev server restarted with its vite cache
cleared; each load-bearing claim (message, `Type`/`Trigger`/`Mechanism`, `# Labels`, `# Attributes`,
absence of `# Logs`) was re-confirmed with `get_issue`. Treat a mismatch after a source edit as
expected churn and re-derive, not as a regression.

Concretely, the app currently holds two parallel families for the same controls: **`SSVELTE-97`-`111`**
(clean module URLs — a freshly restarted server with its vite cache cleared, which is what every key
below cites) and **`SSVELTE-112`-`125`** (the `?t=1787776468813` HMR family, an artifact of editing
sources with the server already running). Only the first is live. Two consequences worth knowing before
touching a source file: a source edit made while `pnpm dev` is running mints the second kind, and a
sweep run against it will look like every key in this table has "regressed"; and an edit that changes
LINE COUNT in a file containing a throw site moves the fingerprint permanently, even after a restart.
The round-3 fix to `src/components/ThrowingWidget.svelte`'s comment was therefore made comment-only and
line-count-preserving, and the check landed: the app's issue total stayed at **125** across it and
`SSVELTE-108` kept `ThrowingWidget.svelte:36:10`.

## S7 — Network capture

Every control below has its OWN assertion reading the exact response body the app read off
`[data-testid="s7-status"]` (an earlier pass of this script had 11 controls behind one shared
decorative assertion; `verify.mjs`'s `s7-*` checks are now per-control).

Those `s7-*` checks are **L**, not W: they assert what the APP saw, which proves the call happened and
that the interceptor did not alter the app's own response — but a capture layer that recorded nothing
at all would leave every one of them green. Network capture has no per-call wire signal (entries sit in
the local ring until the next report's bundle carries them), so the W column here is backed by the
separate **wire-depth capture probe** control: it fires one report whose bundle IS the ring as it
stands, and the `s7-*-wire` checks unzip that bundle and assert the actual `network.json` entries. An
earlier pass of this table marked most of these rows W on the strength of the L check alone.

| Control | Expected | Depth | Evidence |
| --- | --- | --- | --- |
| fetch GET | captured; app reads the real `{"ok":true,...}` body | L/W | `verify.mjs`: `s7-get` (L) + `s7-get-wire` (W) — the probe bundle's `network.json` carries the call under `mechanism: "fetch"` with `status: 200` and the real response body |
| fetch POST JSON | body round-trips through the local API; the REQUEST body is captured | L/W | `verify.mjs`: `s7-post-json` (L — echoes `{"hello":"world","n":42}`) + `s7-post-json-wire` (W) — the probe bundle carries the request body the app sent, asserted on the **`before`-stage entry specifically**. ## Additional finding surfaced during this build

`svelte-boundary-reset` (`verify.mjs`) is not a scenario from the catalog — it documents a real
authoring hazard found while building the S-svelte error-boundary tests: a Svelte 5
`<svelte:boundary>` that has caught an error stops reactively re-rendering its children (including an
outer `{#if route.id === ...}` route-outlet swap) until its `reset()` is explicitly called — navigating
to a different route and back does **not** un-stick it. This is Svelte 5 core behavior, not a
`@bugsee/svelte` defect, so it is not filed in `FINDINGS.md`, but it cost significant build time (a
verify run hung indefinitely after clicking past the boundary — see the fix + full explanation in
`scripts/verify.mjs`'s comments) and is worth flagging for any other Svelte-based sample.
