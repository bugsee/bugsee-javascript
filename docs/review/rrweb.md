# Adversarial review — @bugsee/rrweb

**Reviewed:** 2026-07-26 · **Scope:** packages/rrweb (impl 36 LOC `src/index.ts`, tests 10 LOC `src/index.test.ts`)

**Verdict:** The headline supply-chain worry in the review brief is **unfounded** — the fork is pinned to an **immutable commit SHA**, not a branch, with a `sha512` integrity hash in `pnpm-lock.yaml` and CI on `--frozen-lockfile`; that part is done right. The real defects are in the **type surface**, which is this package's entire reason to exist. The module's two public exports contradict each other: `record` (typed by the fork's own `index.d.ts`, which knows only `maskAttributeFn`) **rejects** the `recordOptions` type the same module exports (which advertises five more fork-only options) — proven with `tsc` (TS2353). This compiles today only by accident: `@bugsee/replay` passes a pre-typed variable, which bypasses excess-property checking. Separately, the built `dist/index.d.ts` declares `EventType` — a real TS `enum`, i.e. a **value** — as a runtime export that `dist/index.js` does not provide, so `import { EventType } from '@bugsee/rrweb'` typechecks and then throws at runtime (verified in Node). Both are latent rather than live because no consumer exercises those paths, hence SEV2 not SEV1. The test thinness is **not** defensible as "nothing to test": the one runtime line is genuinely covered by the one test, but ~85% of the file is a hand-written type contract over a pinned binary, the repo already has a `.test-d.ts` type-test convention (7 files), `vitest.config.ts:11` explicitly excludes that glob in anticipation — and this package has none. The 100% coverage gate passes **vacuously at `0/0` statements**, so it provides zero signal here. Runtime portability and lazy-loading are clean and were verified empirically.

## SEV1

None.

## SEV2

### 1. The wrapper's exported `record` rejects the wrapper's own exported `recordOptions` (the two exports of the "single import point" disagree)

- **Where:** `packages/rrweb/src/index.ts:14` (the `record` re-export) vs `packages/rrweb/src/index.ts:29-36` (the `recordOptions` augmentation)
- **What:** `index.ts:14` re-exports `record` **with the fork's own declared signature**, which comes from `@bugsee/rrweb-record/index.d.ts:8-12` and extends the base options with **only** `maskAttributeFn`. Meanwhile `index.ts:29-36` declares `recordOptions` as the base type plus **six** options: `maskAttributeFn`, `maskAllText`, `unmaskTextClass`, `unmaskTextSelector`, `unblockSelector`, `unmaskInputSelector`. The five non-`maskAttributeFn` options exist in the wrapper's option type but **not** in the parameter type of the wrapper's own `record`. Calling `record({ maskAllText: true })` is a compile error.
- **Why it matters:** This package exists specifically so that "swapping the source touches ONLY this file" (`index.ts:5-6`) and so that consumers have one coherent rrweb contract. A consumer who follows the module's own documented option surface (`index.ts:26-28` explicitly advertises `maskAllText`, `unmaskTextClass`/`unmaskTextSelector`, `unblockSelector`, `unmaskInputSelector`) and passes an object literal gets TS2353. The only reason `@bugsee/replay` compiles is a call-style accident: `register.ts:47` passes `record` as a value into `ReplayRecordFn`, and `recorder.ts` invokes it with a **pre-typed variable**, which suppresses excess-property checking. Any future direct-literal call site — or an inlined refactor in `replay` — breaks the build. These are **privacy** options (fail-closed masking), so a contributor hitting the error and "fixing" it by dropping the option would silently unmask content.
- **Evidence:** Ran `tsc` (repo's own `node_modules/.bin/tsc`, strict, `skipLibCheck`, module paths mapped to the real `packages/rrweb/src/index.ts`, the real fork `index.d.ts`, and the real `rrweb@2.1.0`/`@rrweb/types@2.1.0` d.ts files):
  - Literal with augmented options → `error TS2353: Object literal may only specify known properties, and 'maskAllText' does not exist in type 'recordOptions<eventWithTime> & { maskAttributeFn?: ... }'`
  - Literal with only `maskAttributeFn` → **compiles clean** (confirms the fork's d.ts knows only that one)
  - Same options via a **variable** typed `recordOptions<eventWithTime>` → **compiles clean** (confirms the accident that hides this)
  - `const f: ReplayRecordFn = record` → compiles clean (contravariance, so the defect stays invisible at the seam)
  - Read: `packages/rrweb/node_modules/@bugsee/rrweb-record/index.d.ts:8-12`; `packages/replay/src/recorder.ts:14`; `packages/replay/src/register.ts:47`.
  - Note: the five options **are** genuinely implemented by the pinned bundle — I found them destructured in the top-level `record` entry (minified `Ce`) in `record.js`: `unblockSelector:f=null, unmaskInputSelector:m=null, unmaskTextClass:l=null, unmaskTextSelector:n=null, maskAllText:p=!1`. So this is a **type-declaration** defect, not a runtime one; the fork's shipped `index.d.ts` under-declares its own bundle and the wrapper never reconciles the two.

### 2. Built `.d.ts` declares `EventType` as a runtime export that the built `.js` does not provide

- **Where:** `packages/rrweb/src/index.ts:17` → emitted as `packages/rrweb/dist/index.d.ts:3` and `packages/rrweb/dist/index.d.cts:3`
- **What:** Source says `export type { EventType, eventWithTime, listenerHandler } from '@rrweb/types';`. tsup's dts rollup **drops the `type` modifier**, emitting `export { EventType, eventWithTime, listenerHandler } from '@rrweb/types';` into both declaration files. `EventType` is not a type alias — it is `export declare enum EventType` (`@rrweb/types/dist/index.d.ts:209`), i.e. a real **value**. The emitted `dist/index.js` contains only `export { record } from '@bugsee/rrweb-record';`.
- **Why it matters:** The published type surface lies about the runtime surface. `import { EventType } from '@bugsee/rrweb'` passes `tsc` against the shipped `.d.ts` and then fails at module link time in ESM (and yields `undefined` in CJS interop). This is exactly the class of bug the package is meant to prevent, and it is invisible to every gate the package runs: the wrapper never imports `EventType` itself, so `tsc --noEmit` on `src` is silent, and the sole test never touches it.
- **Evidence:** Deleted-and-rebuilt `dist` via `pnpm --filter @bugsee/rrweb build` to rule out a stale artifact — the value-form export is **reproducible** in both `dist/index.d.ts:3` and `dist/index.d.cts:3`. Then in Node 24: `import * as m from './dist/index.js'` → `exports = [ 'record' ]`; `import { EventType } from './dist/index.js'` → module-job link failure (SyntaxError, no such export). Enum confirmed at `@rrweb/types/dist/index.d.ts:209`.

### 3. A hand-written type contract over a SHA-pinned binary, with the describing types floating on a caret range and zero verification

- **Where:** `packages/rrweb/src/index.ts:11` + `packages/rrweb/src/index.ts:29-36`; `packages/rrweb/package.json:27-29`
- **What:** Three separate hand-maintained descriptions of one bundle now exist and none is checked against the others or against the bundle: (a) the fork's `index.d.ts` (`maskAttributeFn` only), (b) the wrapper's `recordOptions` (six options), (c) the bundle's actual behaviour. Compounding it, the **value** is pinned to an immutable commit (`package.json:27`, `github:bugsee/rrweb#d50d8d7e…`) but the **types that describe that value** are pulled from npm on a caret range — `"rrweb": "^2.1.0"` and `"@rrweb/types": "^2.1.0"` (`package.json:28-29`) — and `index.ts:11` builds the entire public `recordOptions` on top of `BaseRecordOptions` from that floating package.
- **Why it matters:** A future `pnpm update` (or any resolution not governed by the current lockfile) can float `rrweb` to 2.2.x and silently change the option surface the SDK believes the **pinned, unchanged** binary accepts — options could appear that the pinned bundle ignores, or disappear that it still needs. The pin/float asymmetry defeats the reproducibility the SHA pin buys. And nothing would catch it: there is no `.test-d.ts` asserting the option contract, and no runtime test asserting the bundle accepts the six options. `tsc --noEmit` on this package verifies only that a binding named `record` is exported (an `export { record } from …` existence check) — it does not validate a single one of the six option declarations, because the wrapper never calls `record`.
- **Evidence:** `pnpm-lock.yaml:844-852` (specifier vs resolved version); `packages/rrweb/package.json:27-29`; `packages/rrweb/src/index.ts:11`; ran `pnpm --filter @bugsee/rrweb exec tsc --noEmit` → `EXIT=0` with the contradiction in SEV2-1 fully present, confirming the typecheck gate cannot see it. Base `recordOptions` read at `rrweb@2.1.0/dist/rrweb.d.ts:220-252` — it contains **none** of the five augmented options (grep for each returned 0 hits), so the entire delta is unverified hand-written text.

## SEV3

### 1. The 100% coverage gate passes vacuously at `0/0` — it provides no signal for this package

- **Where:** `packages/rrweb/vitest.config.ts:8-13`
- **What:** The package inherits the repo's binding gate (`thresholds: { lines: 100, functions: 100, statements: 100, branches: 90 }`), but `src/index.ts` compiles to a single re-export with no coverable statements, so v8 reports `Statements: 100% (0/0)` with an **empty** per-file table.
- **Why it matters:** The gate is satisfied by construction and would keep passing if the test file were deleted or gutted. `docs/implementation-standards.md:62` treats coverage exclusions as requiring justification; this is not an exclusion but a vacuous pass, which is arguably worse — it reads as a green gate while measuring nothing. No annotation records that.
- **Evidence:** `pnpm --filter @bugsee/rrweb exec vitest run --coverage` → `Test Files 1 passed`, coverage table empty, `Statements : 100% ( 0/0 )`, `Branches : 100% ( 0/0 )`, `Functions : 100% ( 0/0 )`, `Lines : 100% ( 0/0 )`.

### 2. No type test, despite the repo convention and this package being ~85% type surface

- **Where:** `packages/rrweb/src/index.test.ts:1-10`; `packages/rrweb/vitest.config.ts:11`
- **What:** The sole test asserts `expect(typeof record).toBe('function')`. That single assertion is **defensible and genuinely load-bearing** for the runtime line — in ESM a renamed/removed `record` export in the fork fails at link time, so the test collapses. But 26 of the file's 36 lines are type declarations, and there is no `src/index.test-d.ts`. The repo has an established type-test convention — 7 `.test-d.ts` files across `types`, `core` (×4), `opentelemetry`, `protocol` — and this package's own `vitest.config.ts:11` already excludes `src/**/*.test-d.ts` from coverage, i.e. the slot was anticipated and left empty.
- **Why it matters:** Every SEV2 above is exactly what a type test would have caught: an `expectTypeOf(record).toBeCallableWith({ maskAllText: true })` assertion fails on SEV2-1, and an `expectTypeOf<typeof import('./index')>()` value-vs-type assertion catches SEV2-2. Untested failure modes today: fork renames/drops an option, npm `rrweb` floats its option surface, tsup emits a value export for a type-only re-export, the fork's d.ts and the wrapper's augmentation diverge further.
- **Evidence:** `find packages -name '*.test-d.ts' -not -path '*/node_modules/*'` → 7 files, none in `packages/rrweb`. Read `packages/rrweb/src/index.test.ts` in full.

### 3. Missing `publishConfig` while shipping `files: ["dist"]` and `exports` → `./src/index.ts`

- **Where:** `packages/rrweb/package.json:10-18`
- **What:** `exports["."]` points at `./src/index.ts` (correct for in-repo dev), and `files` ships only `dist` — but unlike 42 of the repo's 53 packages there is no `publishConfig` to repoint `exports` at `dist` on publish. If `private: true` (`package.json:4`) is ever lifted, the published tarball's `exports` would reference `src/index.ts`, which is not in `files`.
- **Why it matters:** Bounded today by `private: true`, and this is a **shared** gap rather than an rrweb-specific one — the same omission exists in `bundler-plugin-core`, `electron`, `replay`, `replay-canvas`, `vite-plugin`, `webpack-plugin` (all 7 have a `build` script and `files: ["dist"]`). Flagging for the set, since `@bugsee/replay` cannot ship without `@bugsee/rrweb` shipping too.
- **Evidence:** Scanned all 53 `packages/*/package.json`: 42 have `publishConfig`; the 7 build-producing packages listed above do not. Cross-checked `tsup.config.base.ts:6` which states "`dist` is what `publishConfig.exports` ships".

### 4. Source comment and design docs name a moving branch; the actual pin is a SHA (and a different branch name)

- **Where:** `packages/rrweb/src/index.ts:4` vs `packages/rrweb/package.json:27`
- **What:** The header comment says the dependency is "on github.com/bugsee/rrweb**#bugsee-dist**". The actual specifier is `github:bugsee/rrweb#d50d8d7e0786e095bfaa12bdaadc59b7447ed920`. The installed fork's own `package.json` description says it was "Built from the **bugsee-port** branch". `docs/design/replay.md:3-4` and `:94` also describe the dependency as branch-pinned.
- **Why it matters:** The doc drift understates the engineering quality (a reader concludes the dep is branch-pinned and force-pushable — the exact false premise this review started from) and obscures the real operational fact that matters: bumping the fork requires editing a SHA here. Three artifacts name two different branches and one SHA.
- **Evidence:** `packages/rrweb/src/index.ts:4`; `packages/rrweb/package.json:27`; `packages/rrweb/node_modules/@bugsee/rrweb-record/package.json` (`description`); `docs/design/replay.md:3-4,91,94`.

### 5. `rrweb` (6.6 MB installed) is a runtime `dependencies` entry for a type-only import

- **Where:** `packages/rrweb/package.json:28-29`; used type-only at `packages/rrweb/src/index.ts:11,17`
- **What:** Both `rrweb` and `@rrweb/types` are imported **type-only** and are fully erased — the built `dist/index.js` is one line with no reference to either. Yet both sit in `dependencies`, so installing the SDK pulls the full `rrweb` npm package (6.6 MB on disk, including the replay player) plus `@rrweb/types` (196 KB).
- **Why it matters:** Partially defensible — the emitted `dist/index.d.ts:1,3` imports from both, so they must resolve for downstream `.d.ts` consumers, which is a legitimate reason to keep them out of `devDependencies`. But it sits in tension with the package's stated purpose ("record-only bundle with the replay player tree-shaken out; ~56 KB", `index.ts:4-5`): bundle size is unaffected (tree-shaken, never imported at runtime) but **install** size is not. There is no comment recording that this is deliberate, so a future reader is as likely to "fix" it into `devDependencies` — breaking downstream type resolution — as to leave it.
- **Evidence:** `cat dist/index.js` → single `export { record } from '@bugsee/rrweb-record';`; `du -sh` on the pnpm store paths → 6.6 M and 196 K; `dist/index.d.ts:1,3` confirms the d.ts-level need.

### 6. Two exports are dead across the entire repo

- **Where:** `packages/rrweb/src/index.ts:17` (`EventType`), `packages/rrweb/src/index.ts:21` (`MaskAttributeFn`)
- **What:** Repo-wide grep for both identifiers (excluding `node_modules`, `dist`, `coverage`) returns **only** the three lines inside `packages/rrweb/src/index.ts` itself. No consumer imports either. `MaskAttributeFn` is used once internally at `index.ts:30`; `EventType` is used nowhere at all.
- **Why it matters:** Minor on its own, but `EventType` is the same export that produces SEV2-2 — it is simultaneously unused and actively wrong in the built artifact, so removing it fixes a real defect at zero cost. Verified in-use: `record` (`replay/src/register.ts:8`), `recordOptions` (`replay/src/masking.ts:14`, `replay/src/recorder.ts:10`), `eventWithTime` + `listenerHandler` (`replay/src/recorder.ts:10`).
- **Evidence:** `grep -rn 'EventType\|MaskAttributeFn' packages --include='*.ts'` filtered → 3 hits, all self-referential.

## Checked and found clean

- **Supply-chain pinning (the brief's primary concern) — clean, and better than described.** `package.json:27` pins `github:bugsee/rrweb#d50d8d7e0786e095bfaa12bdaadc59b7447ed920`, an **immutable commit SHA**, not a branch. `pnpm-lock.yaml:1483-1484` resolves it to a content-addressed codeload tarball **with a `sha512` integrity hash**, and `.github/workflows/ci.yml:38` installs with `--frozen-lockfile`. A force-push or branch deletion on the fork therefore **cannot** change what is installed; a tampered tarball fails the integrity check. Verified the fork is reachable and public (`https://github.com/bugsee/rrweb` → HTTP 200; the pinned codeload tarball → HTTP 200), so no auth is needed in CI and the empty `.npmrc` (only `auto-install-peers=true`) is correct. Residual risk is availability-only (repo going private, or GitHub GC'ing the commit if it ever leaves all branches) — worth a vendored fallback eventually, but not a defect today.
- **Runtime portability — clean, verified empirically.** Imported the built ESM bundle in **bare Node with no DOM** (`typeof document === 'undefined'`): it loaded successfully and exported `record`. The fork's only top-level DOM touch (`document.createElement('iframe')` in an `Array.from` polyfill probe) is both feature-guarded and wrapped in `try/catch`, so it never fires on modern runtimes. The CJS build (`dist/index.cjs`) also imports cleanly. The wrapper's own DOM reference (`HTMLElement` at `index.ts:21`) is type-only and fully erased. `tsconfig.json:6-7` correctly widens `lib` to include DOM for this DOM-adjacent package.
- **Lazy-loading — clean, and correctly structured.** `index.ts:14` is a static import, which is right: the wrapper is only ever reached through `@bugsee/replay`, and `packages/browser/src/launch.ts:454` reaches that via `void import('@bugsee/replay')` gated on the `replay` option, with `@bugsee/replay-canvas` separately lazy-imported at `launch.ts:460` only when `replay.canvas` is set. Non-replay consumers never load the 180 KB fork bundle. `browser/src/launch.test.ts:1099,1132,1140` assert the negative cases.
- **Bundle-size and record-only claims — accurate.** The fork bundle gzips to **58,069 bytes ≈ 56.7 KiB**, matching the "~56 KB gzip" claim in `index.ts:5` and `docs/design/replay.md:4`. The bundle's sole export is `record` (`export{Ce as record}`), confirming the replay player is genuinely tree-shaken out.
- **Consistency with the replay-canvas "Build correction (2026-07-22)".** The correction states rrweb 2.1.0 records canvas by **options alone** and that the fork's bundle already ships the canvas recorder — so the wrapper should expose **no** canvas-specific export. Confirmed: the wrapper exposes none, and `recordCanvas` (20 occurrences), `dataURLOptions` (28) and `sampling` (10) are present in the pinned bundle and reachable through the inherited base `recordOptions`. `replay/src/recorder.ts:22-28` consumes them via the `CanvasRecordConfig` seam. The superseded `@bugsee/rrweb/canvas` entry proposed in `docs/design/replay-canvas.md:230` was correctly **not** built.
- **The fork's augmented options are real.** Independently verified all six against the pinned binary by locating the top-level `record` entry's option destructure in `record.js`: `maskAttributeFn`, `maskAllText:p=!1`, `unmaskTextClass:l=null`, `unmaskTextSelector:n=null`, `unblockSelector:f=null`, `unmaskInputSelector:m=null` are all destructured from the user options object and threaded into the snapshot layer. So SEV2-1/SEV2-3 are declaration defects, **not** silent fail-open masking — masking works at runtime.
- **`| null` on the augmented selectors is honest.** I suspected the intersection with the base type would narrow `string | null` back to `string`, making the advertised `null` unassignable. Verified with `tsc`: assigning `null` to `unblockSelector`, `unmaskTextClass`, `unmaskTextSelector`, `unmaskInputSelector` **compiles clean** — the base type declares none of them, so there is no intersection to narrow. Hypothesis dropped.
- **No `any` leaks.** The public surface contains no `any`. `recordOptions<T = unknown>` adds a default the base type lacks, but `unknown` is the safe choice and both consumers instantiate it explicitly (`recordOptions<eventWithTime>` at `replay/src/recorder.ts:14`, `recordOptions<unknown>` at `replay/src/masking.ts:80`).
- **Consumer contract — no dead or misused imports among the four live exports.** `replay/src/masking.ts:80-81` uses `Pick<recordOptions<unknown>, 'maskAllInputs' | 'maskInputOptions' | 'maskAttributeFn' | 'maskAllText'>`, which is a genuine compile-time consumer of the augmentation (`Pick` errors on absent keys) — this is the one place the augmentation is load-bearing at type level. `@bugsee/replay-canvas` correctly does **not** depend on `@bugsee/rrweb` directly; it goes through `@bugsee/replay`'s `CanvasRecordConfig` seam (`replay-canvas/src/canvas-config.ts:6`).
- **Gates pass.** `pnpm --filter @bugsee/rrweb exec tsc --noEmit` → exit 0. `vitest run` → 1/1 passing.
- **Working tree untouched.** `git status --short packages/rrweb` → empty, confirmed both mid-review and at completion. All probe files were written to the scratchpad; the only files written under `packages/rrweb` were regenerated `dist/` and `coverage/` artifacts, both gitignored (`.gitignore:2,3`).
