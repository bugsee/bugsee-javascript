# Adversarial review — @bugsee/types

**Reviewed:** 2026-07-26 · **Scope:** packages/types (impl 32 LOC `src/index.ts`, tests 58 LOC `src/index.test-d.ts`)

**Verdict:** Structurally healthy for a tier-0 type-only package. There is **no runtime code**, so the absence of `*.test.ts` / a `test` script is **defensible**, not a coverage-gate violation — `tsc --noEmit` is the correct test runner and `src/index.test-d.ts` is a real, mutation-resistant type test for most of the surface. Runtime portability is clean (zero `node:*` imports, zero DOM references, zero `globalThis` reaches, zero `any`). Android parity on all four public unions is **exact** (verified against the Java enums). The real defects are (a) one **surviving mutation** in the type test that leaves the package's single most load-bearing property — declaration *mergeability* — unprotected, and (b) **three dead exports** (`AppToken`, `NameHookMapping`, `NameHubMapping`) that type APIs which either take a plain `string` or do not exist at all. Neither breaks a consumer today; both are contract-hygiene debt in the package where such debt is most expensive. Doc drift (`NameServiceMapping`) is stale but harmless.

## SEV1

None.

## SEV2

### 1. The `interface → type` mutation survives — the type test does not protect declaration mergeability

- **Where:** `packages/types/src/index.test-d.ts:55-57` (assertions) against `packages/types/src/index.ts:27,29,32` (the three merge targets)
- **What:** The only assertions covering the three declaration-merge targets are `Expect<Equal<keyof NameExtensionMapping, never>>` (and the two siblings). These assert *emptiness*, which is preserved by converting `export interface NameExtensionMapping {}` into `export type NameExtensionMapping = {};`. But that conversion destroys the entire purpose of these types: a `type` alias **cannot** be declaration-merged. The whole cross-package extension-typing mechanism would silently stop working, and the type test would stay green.
- **Why it matters:** These three interfaces have exactly one job — to be augmented from other packages. `packages/core/src/extension-registry.ts:1,11,13,15` derives `registerExt`/`ext`/`hasExt` from `keyof NameExtensionMapping`, and `packages/performance/src/extension.ts:19-23` augments it via `declare module '@bugsee/types' { interface NameExtensionMapping { performance: PerformanceApi } }`. If the target became a `type`, every such augmentation site breaks and `client.ext('performance')` loses its typing. The project's binding mutator-loop standard (`docs/implementation-standards.md` §2 / CLAUDE.md #2) requires that no injected mutation survive undetected — this one does. A one-line fix exists (assert an augmented-in-a-scratch-module key, or `Expect<Extends<{ x: 1 }, NameExtensionMapping & { x: 1 }>>`-style mergeability probe).
- **Evidence:** Ran the mutation in an isolated scratch copy of both files (source untouched):
  - baseline `tsc --noEmit --target ES2022 --module ESNext --moduleResolution Bundler --strict --lib ES2023 src/index.ts src/index.test-d.ts` → `BASELINE_EXIT=0`
  - after rewriting all three to `export type NameXMapping = {};` → `MUTATED_EXIT=0` (**mutation survived, zero diagnostics**)
  - Control: the same harness *does* catch other mutations (`Brand`'s brand made optional → 4 errors, exit 2; dropping `'low'` from `SeverityName` → error at `index.test-d.ts:51`, exit 2; `AppToken = Brand<string,'IssueId'>` → exit 2). So the harness is sound and this specific gap is real, not a harness artifact.

### 2. `AppToken` is a dead branded type — the one string every user passes is unbranded

- **Where:** `packages/types/src/index.ts:10` (`export type AppToken = Brand<string, 'AppToken'>`)
- **What:** `AppToken` has **zero consumers** anywhere in the repo outside `packages/types` itself. Every real entry point and internal carrier takes a plain `string`: `packages/node/src/launch.ts:353,853`, `packages/browser/src/launch.ts:256,547`, `packages/bugsee/src/launch.ts:21`, `packages/bugsee/src/node.ts:17`, `packages/core/src/bugsee-api.ts:18`, `packages/core/src/bundle-assembler.ts:31`. Its three sibling brands are genuinely applied (`AccessToken`/`IssueId`/`RecordingId` in `packages/core/src/bugsee-api.ts:2,31,61` and `packages/core/src/transport.ts:3`), so this is an outlier, not a package-wide stylistic choice.
- **Why it matters:** Two consequences. (a) The brand's stated purpose — "an opaque `T` that can't be mixed with plain `T` or other brands" (`index.ts:6`) — is unrealised precisely where confusion is most likely and most damaging: nothing stops a caller passing an access token, a user id, or an empty string to `launch()`. (b) It is verifiable design-doc drift: `docs/design/sdk-design.md:925` specifies `appToken: AppToken` inside `BugseeOptions`, and `sdk-design.md:91` lists `AppToken` among the "branded identifier types". Either apply the brand at the boundary (with a `toAppToken()`-style validator) or delete the type; shipping an unapplied brand plus 8 type assertions about it is the worst of both.
- **Evidence:** Repo-wide `grep -rn 'AppToken' --include='*.ts' --include='*.tsx' --include='*.md'` (excluding `node_modules`, `dist`, `coverage`, `.nuxt`, `.svelte-kit`) returns only: `packages/types/src/index.ts:10`, 8 assertion lines in `packages/types/src/index.test-d.ts`, `packages/types/README.md:3`, the two design-doc lines, and `hashAppToken(appToken: string)` in `packages/node/src/data-location.ts:24,113,118` — which takes `string`, not `AppToken`.

### 3. `NameHookMapping` and `NameHubMapping` are dead exports typing APIs that do not exist

- **Where:** `packages/types/src/index.ts:29` and `packages/types/src/index.ts:32`
- **What:** Neither type is imported, referenced, or augmented anywhere in the monorepo outside `packages/types`. `index.ts:30` documents `NameHubMapping` as the "Event-hub typing target for `client.hubs.<name>` (design §16.2)" — but `client.hubs` does not exist: the `Client` contract in `packages/core/src/contracts.ts` has no `hubs` member, and `grep -rn 'hubs:' packages/core/src` returns nothing (only prose comments mention "hubs"). Likewise `HookName` — the `keyof NameHookMapping` consumer specified at `docs/design/sdk-design.md:1166,1824` — does not exist anywhere in `packages/`.
- **Why it matters:** This is exactly the drift CLAUDE.md flags as as-built delta: *"the design-doc 'event hubs' layer was **removed** during implementation — interceptors are themselves listenable."* The types outlived the layer they were built for. In a tier-0 package they are permanent public API that every downstream package transitively sees, they carry `biome-ignore` suppressions to stay lint-clean, and `index.test-d.ts:56-57` spends assertions pinning their (dead) emptiness — which reads as coverage but validates nothing anyone consumes. `NameExtensionMapping` is the live one and should be the only survivor unless the hook/hub layer is actually planned.
- **Evidence:** `grep -rn 'NameHookMapping\|NameHubMapping\|NameExtensionMapping' --include='*.ts' packages/` excluding `packages/types/` returns **13 hits, all `NameExtensionMapping`** (`core/src/extension-registry.ts:1,5,11,13,15,37`, `core/src/client.ts:14,146,147`, `core/src/extension-registry.test.ts:5,7`, `core/src/client.test.ts:47`, `performance/src/extension.ts:20`) and **zero** for the other two. `grep -rn 'HookName' --include='*.ts' packages/` → zero hits.

## SEV3

### 4. `README.md` and `package.json` advertise `NameServiceMapping`, which the package does not export

- **Where:** `packages/types/README.md:3` and `packages/types/package.json:6`
- **What:** Both list `NameServiceMapping` as one of "the declaration-merge targets" this package provides. It is not exported — `packages/types/src/index.ts:24-25` explicitly says the opposite: *"(Services are resolved by typed ServiceToken values from @bugsee/service, NOT a name→type map.)"*
- **Why it matters:** `package.json.description` is published registry metadata and `README.md` is included by npm regardless of the `files` allowlist, so both would ship a claim contradicted by the `.d.ts`. A consumer following the README would write a `declare module '@bugsee/types' { interface NameServiceMapping {...} }` block that compiles (module augmentation happily creates a new interface) but is wired to nothing.
- **Evidence:** `docs/PROGRESS.md:220` records the removal verbatim: *"every `declare module '@bugsee/types'` service block is gone and `NameServiceMapping` is removed from `@bugsee/types` (`NameExtension`/`Hook`/`Hub` mappings stay)"*; `docs/design/internal-object-di.md:38` says the same. `PROGRESS.md:16`'s package table is already correct — only these two files are stale.

### 5. The exported `Brand<T, B>` generic is untested and unused, and the branding idiom is duplicated

- **Where:** `packages/types/src/index.ts:7`
- **What:** `Brand` is public API but is **not imported** by `index.test-d.ts` (its import list at `index.test-d.ts:5-17` omits it), so it is only exercised indirectly through the four `string` aliases. Nothing outside `packages/types` uses it either. Meanwhile `packages/service/src/index.ts:25-33` re-invents branding independently with a `readonly __type?: T` phantom field rather than reusing this generic.
- **Why it matters:** Two untested degrees of freedom: `Brand` over a **non-string** base (`Brand<number, 'X'>`, `Brand<{a:1}, 'X'>`) and **brand-tag stability** (`Equal<Brand<string,'X'>, Brand<string,'X'>>`) are both unasserted, so a refactor of `Brand` that only breaks non-string bases would ship silently. And the duplicated idiom means a future fix to one branding mechanism will not reach the other. Low blast radius today (all current brands are over `string`), hence SEV3.
- **Evidence:** `grep -rn '\bBrand\b' --include='*.ts' packages/*/src` excluding `packages/types/` → zero hits. `grep -rn 'unique symbol\|__brand\|__type' --include='*.ts' packages/*/src` → only `packages/types/src/index.ts:4` and `packages/service/src/index.ts:33`.

### 6. `AttributeValue`'s `string[]` member diverges from the Android-canonical attribute domain and is asymmetric

- **Where:** `packages/types/src/index.ts:21` (`export type AttributeValue = string | number | boolean | string[]`)
- **What:** Android — the stated API and architecture parity target — documents its attribute value domain as string/number/boolean, with everything else coerced: *"Note that strings, numbers and boolean values are returned as is, for objects of other types string representation is returned"* (`android/sdk/library/src/main/java/com/bugsee/library/BugseeInternal.java:1089-1091`, over `setAttribute(@Nullable String, @Nullable Serializable)` at `:1070-1073`). The JS type adds `string[]` as a first-class member but excludes `number[]` and `boolean[]`, which is arbitrary — there is no property of the wire format that admits one and not the others.
- **Why it matters:** `AttributeValue` is the widest-reach type in this package: it flows into `packages/core/src/environment.ts:16,40` (`setAttribute`), `packages/core/src/client.ts:153`, `packages/protocol/src/wire.ts:95` (`attrs: Record<string, AttributeValue>`), `packages/node/src/request-context-store.ts:28,51`, and is re-exported as curated public API from `packages/core/src/index.ts:16` and `packages/bugsee/src/index.ts:9`. A user who types an attribute as `string[]` is promised cross-platform behaviour the mobile-canonical model does not define. **Caveat, stated plainly:** I did **not** verify how the backend ingests an array-valued attribute — that determines whether this is a parity wart or a real data-loss path, and it should be checked before acting.
- **Evidence:** Android enum/API sources read directly (paths above). JS consumer list from `grep -rn 'AttributeValue' --include='*.ts' packages/*/src`.

### 7. `SeverityName` conflates the canonical set with the `low` alias, giving `severityFromWire` a return type wider than its codomain

- **Where:** `packages/types/src/index.ts:19`
- **What:** `SeverityName` is a single flat union of the 5 canonical names plus the `low` iOS alias. There is no canonical-only sub-type, so every producer *and* consumer of a severity shares one type. `packages/protocol/src/levels.ts:69` declares `severityFromWire(value: number): SeverityName` but its switch (`:70-83`) can only ever return the 5 canonical names — `'low'` is unreachable in its output, as the package's own test asserts (`packages/protocol/src/levels.test.ts:101`: `expect(severityFromWire(severityToWire('low'))).toBe('verylow')`).
- **Why it matters:** Any consumer writing an exhaustive `switch` over a `severityFromWire` result is forced to author a `case 'low':` branch that can never execute — which under this repo's binding per-package gate (100% line/fn/stmt, ≥90% branch) becomes an uncoverable branch needing a `/* v8 ignore */` escape. Splitting into `type CanonicalSeverityName = 'verylow'|'medium'|'high'|'critical'|'blocker'` and `type SeverityName = CanonicalSeverityName | 'low'` (narrowing `severityFromWire`'s return to the former) removes the hazard with no API break. No such consumer exists today, hence SEV3.
- **Evidence:** `levels.ts:54-62` (`SEVERITY_BY_NAME` maps both `verylow` and `low` → `Severity.VeryLow`), `levels.ts:69-84` (the switch), `levels.test.ts:66,101`.
