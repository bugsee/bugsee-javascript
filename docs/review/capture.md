# Adversarial review — @bugsee/capture

**Reviewed:** 2026-07-26 · **Scope:** `packages/capture` (impl 2256 LOC across 17 files, tests 3702 LOC across 17 files; 243 tests, 100 % line/fn/stmt, 98.94 % branch)

**Verdict:** The tests are genuinely strong — **37 of 39 targeted mutations were caught**, including every one aimed at the body size cap, the Content-Type gate, the master `captureNetworkBodies` toggle, the default sanitizer, self-isolation, the decorator seam and all six un-patch paths. This is not a package with weak tests. It is a package whose tests are **uniformly synthetic**: not one test in 3702 lines constructs a real `Response` or a real `ReadableStream`, and `reader.cancel()` is always a fake that resolves instantly (`fetch-interceptor.test.ts:412`). That single substitution hides the most serious defect here: on a real teed `Response` body, `await reader.cancel()` **never settles** until the app also drains or cancels its own branch, so the over-cap path at `fetch-interceptor.ts:162` suspends forever — the `size_too_large` amendment is never emitted, and the buffered chunks + reader + closure leak once per over-cap response, for the process lifetime. Four other SEV1s are real host-behavior or privacy breaches, all empirically reproduced: a throwing request decorator propagates out of `fetch()`/`xhr.send()` **and the request is never dispatched**; a hostile `console.log` argument makes the host's `console.log` throw **and swallows the app's own log**, reachable with the default formatter; URL query strings are captured verbatim on every source (the protocol package ships `sanitizeParams` and `REDACTED_URL_ENCODED` for exactly this, with zero callers); and form-urlencoded/plain-text bodies bypass key redaction entirely while *this package* stamps the very Content-Type that lets them past the gate (`password=hunter2&api_key=K123`, verified end-to-end through the default sanitizer). Finally, the umbrella amplifies the known core `InterceptorBase` defect: one throwing leaf kills all five leaves, every platform `additionalSources` (including node:http), **and every capture provider registered after `network`** — which in both `browser` and `node` is everything except console logs.

**On the brief's prior — the code agrees, with three corrections:**
- Confirmed: shared runtime-portable tier (zero `node:*`/DOM imports; every global read is inside a lazy getter closure, nothing evaluated at import time); `#gateBody` does run first on every event (`network-provider.ts:91`); `additionalSources` is the platform seam (`install-network-capture.ts:90`); the fetch `clone()`+bounded-read+`cancel()` design does preserve the app's response (verified against a **real** `Response`: `bodyUsed === false`, `body.locked === false`, and the app read all 200 000 bytes while the SDK capped at 16).
- **Correction 1:** the brief's "does a throw inside the interceptor propagate into the host's call" concern is *not* about the emitter — `MultiKeyEmitterBase.emit` isolates every listener (`core/src/emitter.ts:88-94`), so no subscriber can break a host call. The real escape hatches are the three code paths that run **outside** `emit`: the decorator registry, the console formatter, and `setRequestHeader`. All three confirmed.
- **Correction 2:** `captureNetworkBodies` **is** correctly plumbed from the launch option down into the interceptors on all five platforms (`browser/src/launch.ts:425-427`, `node/src/launch.ts:598-608`, `webworker`, `webview`, `vercel-edge`), so "off" really does skip cloning. Not a gap.
- **Correction 3:** the `runFilter` core defect does **not** throw into the host on this package's two paths — the emitter swallows it. Here it is pure silent data-loss.

## SEV1

### 1. `await reader.cancel()` on a teed `Response` branch never settles — over-cap bodies never get their `size_too_large` amendment, and the read frame + up to `maxBodyBytes` of chunks leak permanently, once per over-cap response

- **Where:** `packages/capture/src/fetch-interceptor.ts:162` (`await reader.cancel();` on the over-cap path) and `packages/capture/src/fetch-interceptor.ts:169` (`await reader?.cancel();` on the read-error path), inside `readBoundedBody` (`:134-177`), driven from `#captureResponseBody` (`:270`).
- **What:** `Response.clone()` is specified as *tee the body's stream* (WHATWG Fetch), and `ReadableStreamTee`'s cancel algorithm returns a **shared `cancelPromise` that is only resolved once BOTH branches are cancelled**. The SDK cancels its branch and `await`s that promise before returning `{ reason: 'size_too_large' }`. If the application has not (yet) drained or cancelled its own branch, the `await` never resumes.
- **Why it matters:** Three consequences, all on the default configuration (`captureBodies` defaults to `true` at `:235`, `maxBodyBytes` to 20480 at `:236`):
  1. **The amendment is never emitted.** Every over-cap response silently produces *no* `no_body_reason` at all — the wire data is wrong, and the viewer cannot distinguish "no body" from "body too large".
  2. **Unbounded memory growth.** The suspended async frame retains `chunks[]` (≤ 20 KB), the stream reader, the live tee branch, and the closure over `resHeaders`/`url`/`method`/`id`/`this`. One leaked frame **per over-cap response** — on a Node server or a long-lived SPA this accumulates without bound. This is the exact failure the "bounded read" design exists to prevent.
  3. The same hang sits on the read-error path (`:167-174`), where the `catch` also `await`s `cancel()`.
  A very common shape triggers it: `fetch()` whose response body the app never consumes (a status check, an error branch that ignores the body, a `HEAD`-ish probe).
- **Evidence:** Probe `R8a` against the **real** `Response` API — a 400 KB stream-backed response with `maxBodyBytes: 20480`:
  `app NEVER touched the body → events = [{"stage":"before"},{"stage":"complete"}]` (300 ms elapsed, **no amendment**); then after `await res.text()`: `events = [..., {"stage":"complete","override":true,"reason":"size_too_large"}]`. Probe `R8b` (a `cancel()` that never settles) reproduces the same on the error path.
  Isolated stream-level probes: `S1` — read 21 504 bytes of a stream-backed `Response.clone()`, then `reader.cancel(): PENDING after 400ms`, `res.bodyUsed === false`; `S4` — still pending after 500 ms; `S2`/`S3` — settles the instant the app drains (`true`) or cancels (`true`). Spec control `E4` — a plain `ReadableStream.tee()` branch cancel: `PENDING after 300ms`. Counter-control `E1/E2/E3` — a *buffered* (string-backed) `Response` in undici settles immediately, which is why the small-body tests pass and this is invisible today.
- **Why no test catches it:** every test substitutes `cancel: () => Promise.resolve()` (`fetch-interceptor.test.ts:412`, `:506`) or a plain object literal. Mutations `F3` (`>` → `>=`) and `F4` (delete the cap) were both **CAUGHT**, so the cap logic is tested — but the *consequence* of the cancel is not.

### 2. A throwing request decorator escapes into the host's `fetch()` / `xhr.send()` **and the request is never dispatched**

- **Where:** `packages/capture/src/request-decorator.ts:51-55` (`run()` calls `decorate(request)` with no guard), reached at `packages/capture/src/fetch-interceptor.ts:320` — which executes **before** the dispatch at `:328` — and at `packages/capture/src/xhr-interceptor.ts:191`, before the dispatch at `:227`. A second variant: `packages/capture/src/xhr-interceptor.ts:199` (`originalSetHeader.call(this, name, value)`) throws when a decorator returns a header name the platform rejects.
- **What:** Decorators are the one sanctioned mutation seam, and `request-decorator.ts:9-10` binds them to *"MUST be synchronous and fast — any blocking/latency would itself be a behavior change"*. The registry never considers the throwing case. Because `run()` is invoked before the underlying `fetch`/`send`, a decorator exception does not merely lose capture — it **cancels the application's network request** and surfaces a foreign exception at the call site.
- **Why it matters:** The shipped first consumer is the trace-context propagator (`packages/capture/src/traceparent.ts:141-167`), which calls user/extension-supplied seams: `options.getActiveSpan()` (`:148`), `span.getTraceId()`/`getSpanId()` (`:154`), `options.getBugseeState?.()` (`:158`), and `options.resolveOrigin` (`:132`). A throw from any of them — an APM extension mid-teardown, a span object in an unexpected state — takes down **every outgoing request in the host application**. This is the single most direct violation of the binding rule in the package.
- **Evidence:** Probe `P2a` — `threw = Error: decorator boom`, `dispatched = 0` (the real fetch was never called). Probe `P2b` — `xhr.send()`: `threw = Error: decorator boom`, `sent = 0`. Probe `P2c` — a decorator returning `{'bad header': 'v'}`: `threw = Error: InvalidCharacterError: bad header`, `sent = 0`. Mutation `D1` (registry treats every return as an addition) was **CAUGHT** (2 failures), so the registry's happy path is tested; the throwing path has no test at all.

### 3. The console interceptor formats arguments outside any guard — a hostile argument makes the host's `console.log()` throw **and swallows the app's own log**

- **Where:** `packages/capture/src/console-interceptor.ts:96-105` — the emitted payload is built with `this.#format(args)` *inside* the `try`, but the block is `try`/**`finally`**, not `try`/`catch`; the pass-through `original.apply(con, args)` is at `:106`, after the block.
- **What:** Any exception raised while formatting propagates out of the patched `console.log`, and `:106` is never reached, so the application's own log line is lost as well. Reachable **with the default formatter and zero configuration**: `formatConsoleArgs` (`:47`) → `stringifyArg` (`:33`) → `jsonSafeStringify` (`:41`) for any object argument. Despite its docstring (*"`JSON.stringify` that never throws"*), `packages/util/src/json-safe-stringify.ts:11` only guards circular references and `BigInt` — a throwing `toJSON()` or a throwing property getter propagates straight through `JSON.stringify`. Two narrower variants on the same line-set: `:38` (`arg.stack` on an `Error` subclass with a throwing getter) and `:43` (`String(arg)` on a value with a hostile `Symbol.toPrimitive`).
- **Why it matters:** `console.log` is the most-called API in a JS application. Objects with a throwing `toJSON` are ordinary in the wild (ORM model instances, revoked `Proxy` objects, lazily-hydrated view models). Installing Bugsee turns `console.log(model)` from a harmless call into an application-breaking throw. A platform that injects its own `format` (the documented Node `util.format` seam, `:59`) inherits the same hole.
- **Evidence:** Probe `P4b`, default formatter, **no custom options**: `console.log({ toJSON() { throw new Error('toJSON boom') } })` → `threw = Error: toJSON boom`, `passthrough = 0`. Probe `P4a` with an injected throwing `format`: `threw = Error: format boom`, `passthrough calls = []`. The re-entrancy guard is well tested (mutation `C2` **CAUGHT**) and the pass-through is well tested (control `C4` **CAUGHT**, 2 failures) — but no test drives a throwing formatter or a hostile argument.

### 4. Privacy: URL query strings are captured verbatim on every source — no URL scrubbing exists anywhere in the SDK

- **Where:** the URL is written unmodified at `packages/capture/src/fetch-interceptor.ts:311` → `:341`, `:365`, `:386`, `:279`; `packages/capture/src/xhr-interceptor.ts:157` → `:213`, `:262`, `:281`; `packages/capture/src/web-socket-interceptor.ts:94`; `packages/capture/src/sse-interceptor.ts:92`; `packages/capture/src/web-transport-interceptor.ts:91`. The only redaction stage, `packages/capture/src/network-provider.ts:31-45`, touches **only** `custom.headers` (`:36`) and `custom.body` (`:38-40`) — `event.url` is never passed through any sanitizer.
- **What:** Secrets in query strings (`?api_key=`, `?token=`, `?password=`, signed-URL signatures, session ids, SSO `code`/`id_token` on OAuth callbacks, WebSocket `?token=` handshakes) are stored and uploaded in the clear. `@bugsee/protocol` already ships the exact tool for this — `sanitizeParams` (`protocol/src/sanitize.ts:23-31`, key-denylist redaction over a flat param map) and the URL-encoded token `REDACTED_URL_ENCODED` (`protocol/src/sensitive.ts:7`) — and **neither has a single caller anywhere in the monorepo** (independently confirmed in `docs/review/protocol.md` SEV3 #15, which notes the token *"was created for a URL scrubber that does not exist yet"*). The denylist that would catch these is already populated (`protocol/src/sensitive.ts:41-60`: `token`, `api_key`, `apikey`, `password`, `secret`, `access_token`, …).
- **Why it matters:** `redactShapes` (`protocol/src/shapes.ts:47`) is *not* a substitute — it only matches five literal secret shapes (JWT, AWS key id, Stripe, GitHub) and is in any case never applied to the URL. A bare `?api_key=K123` matches nothing.
- **Evidence:** Probe `P9b` — the full source→provider→aggregator path with the default sanitizer on. The `authorization` header was correctly redacted to `"<redacted>"`, while the serialized entry carried `"url": "https://api/x?api_key=SECRET123&Authorization=Bearer%20xyz"` on all three events (`before`, `complete`, and the body amendment). Probe `P9a` confirms it at the interceptor level.

### 5. Privacy: form-urlencoded and plain-text bodies bypass key redaction — and this package stamps the Content-Type that lets them past the gate

- **Where:** `packages/capture/src/network-body.ts:40` (`return { body: String(body), contentType: FORM_URLENCODED_TYPE }`) and `:36` (`contentType: TEXT_PLAIN_TYPE`), consumed at `packages/capture/src/fetch-interceptor.ts:334-336` and `packages/capture/src/xhr-interceptor.ts:205-207` — *"Reflect the runtime-implied Content-Type only when the caller set none (so the captured headers match the wire and the downstream gate keeps the body)"*.
- **What:** `sanitizeBody` (`protocol/src/sanitize.ts:76-84`) applies the recursive key denylist **only to JSON media types**; every other type gets `redactShapes` alone. Form-urlencoded key redaction is an acknowledged follow-up in that file's docstring. Meanwhile this package *synthesizes* the `application/x-www-form-urlencoded` / `text/plain` header that the body gate (`gateNetworkBody`, `protocol/src/sanitize.ts:118-140`) requires in order to keep the body — without the stamp the body would be dropped as `no_content_type` by default (`captureBodyWithoutType` defaults to `false`, `network-provider.ts:85`). So the SDK actively creates the condition under which the credential is retained.
- **Why it matters:** `new URLSearchParams({ username, password })` is the canonical HTML-form login body. The classic form POST is exactly the request whose body must never be stored.
- **Evidence:** Probe `R1a` — full path, default options, default sanitizer:
  `custom.headers = {"content-type":"application/x-www-form-urlencoded;charset=UTF-8"}` (stamped by the SDK — the caller set none) and `custom.body = "username=bob&password=hunter2&api_key=K123"` — **in the clear**. Probe `R1c`, a string body: `"password=hunter2&ssn=123-45-6789"`, verbatim. Control `R1b` (the same credentials with `content-type: application/json`) correctly yields `{"username":"bob","password":"<redacted>"}` — so the harness and the JSON path are sound; the gap is media-type-specific. Mutations `N3`/`N4` (drop the implied Content-Type) were both **CAUGHT**, confirming the stamping is deliberate and pinned.

### 6. One throwing leaf `onActivate` kills the entire network umbrella — all five leaves, every platform `additionalSources`, **and every capture provider registered after `network`** — permanently, while leaking the patches already installed

- **Where:** `packages/capture/src/network-interceptor.ts:47` — `this.#offs = this.#sources.map((source) => source.onAny(...))`. The assignment happens only after the whole `map` completes, and `map` is unguarded. Leaf order is fixed at `packages/capture/src/install-network-capture.ts:71-89` (**fetch is index 0**). The subscription is made from `packages/capture/src/network-provider.ts:86` inside `onStart`, also unguarded.
- **What:** Subscribing to a leaf drives its `onActivate` (subscriber-presence activation). Every leaf's `onActivate` writes a runtime global — `fetch-interceptor.ts:298`, `xhr-interceptor.ts:136-138`, `web-socket-interceptor.ts:78`, `sse-interceptor.ts:76`, `web-transport-interceptor.ts:74` — which throws in strict mode against a frozen/non-writable global (SES/lockdown, a hardened realm, `Object.freeze(globalThis)`, or another SDK that installed a non-configurable accessor). The three constructor-subclassing leaves additionally throw if the global is present but not a constructor (`class extends original`).
  When leaf 0 throws: (a) the exception propagates out of `umbrella.onAny()` → `provider.onStart()` → `coordinator.start()`; (b) `#offs` is never assigned, so the umbrella's `onDeactivate` (`:54-59`) unsubscribes **nothing** and any leaf already subscribed stays patched forever; (c) the umbrella's `#active` is already `true` (core `interceptor-base.ts:46`), so it is never retried.
- **Why it matters:** This package *amplifies* the known core defect from "one source dies" to "all network capture dies". Worse, `capture-coordinator.ts:69-71` iterates providers unguarded, and `network` is registered **second** in both platforms — `packages/browser/src/launch.ts:428` (before system traces `:429`, `:435` and user events `:444`) and `packages/node/src/launch.ts:611` (before `:624` and system events `:630`). So a single frozen `globalThis.fetch` silently reduces the SDK to console logs only, with `launch()` reporting success.
- **Evidence:** Probe `P3a` — `installNetworkCapture({ fetchTarget: <frozen> })`, then `interceptor.onAny(...)`: `threw = TypeError: Cannot assign to read only property 'fetch'`. Probe `P3b` — after clearing the failure, a second subscription: `installs = 0` (**never retried**). Probe `R4a` — a healthy leaf followed by a throwing leaf: `goodInstalls = 1`, and after `umbrella.removeAllListeners()` still `goodInstalls = 1, uninstalls 0` (the healthy leaf's patch is **never removed**); re-subscribing produces no re-activation. Control mutation `U1` (umbrella `onDeactivate` does not unsubscribe) was **CAUGHT**, so the happy-path teardown is tested — the partial-failure path is not.

## SEV2

### 7. Reusing an `XMLHttpRequest` instance emits N duplicate `complete`/`error` events carrying a **stale url/id/method** attached to the **current** response's status, headers and body

- **Where:** `packages/capture/src/xhr-interceptor.ts:222-225` — four listeners are added on **every** `send()` and never removed — combined with `:154-160`, where `open()` installs a *new* state object while the previously-registered closures keep capturing the *old* one (`:182`).
- **What:** XHR instance reuse (`open`/`send`, then `open`/`send` again) is legal and common in older code and in XHR-based polyfills. Each `send()` stacks another set of listeners bound to that send's state. When any subsequent response fires `load`, **all** accumulated listeners run: `#complete(this, staleState)` (`:254-273`) reads `xhr.status`, `xhr.getAllResponseHeaders()` and `xhr.responseText` from the **live** object while writing `state.id`, `state.url` and `state.method` from the **stale** one.
- **Why it matters:** Data integrity and privacy: request 5's response **body** is stored under request 1's URL. It also produces N-fold event duplication and linear listener growth on a long-lived reused XHR (a polling loop reusing one instance leaks a listener set per poll).
- **Evidence:** Probe `P5a` — two requests on one instance: the second `load` emitted `{"stage":"complete","id":"x1","url":"https://api/first","status":200}` **and** `{"stage":"complete","id":"x2","url":"https://api/second","status":200}`; `load` listener count = 2. Probe `R6a` — five sends on one instance: `load listeners = 5`, and a single `load` fired **5** `complete` events (`x1:https://api/0` … `x5:https://api/4`), all reading the same live response.

### 8. Un-patching restores a saved reference rather than un-wrapping — it clobbers a competing SDK's patch, and two Bugsee interceptors on one target leave the global permanently wrapped by a dead one

- **Where:** all six sources restore by blind assignment: `packages/capture/src/fetch-interceptor.ts:301-306`, `packages/capture/src/xhr-interceptor.ts:141-149`, `packages/capture/src/web-socket-interceptor.ts:81-86`, `packages/capture/src/sse-interceptor.ts:79-84`, `packages/capture/src/web-transport-interceptor.ts:78-83`, `packages/capture/src/console-interceptor.ts:111-119`.
- **What:** The classic monkey-patch-restore bug. If another library patched over us between our install and our uninstall, `set(this.#original)` **destroys their wrapper**. If two Bugsee interceptors wrap the same target and are torn down in non-LIFO order, the global is left holding the first one's orphaned wrapper.
- **Why it matters:** Coexistence with another APM SDK (Sentry, Datadog, New Relic all patch `fetch`/`XHR`/`console`) is the normal production condition, and Bugsee's uninstall runs on `client.stop()`/relaunch. Silently disabling a competitor's instrumentation is a support incident, not a Bugsee bug report. The second variant is reachable in-repo: `installNetworkCapture` de-dupes leaves per **carrier** (`install-network-capture.ts:68-70`), so two tiers holding different carriers in one realm (e.g. `@bugsee/browser` plus `@bugsee/webview`, which passes its own carrier at `webview/src/launch.ts:276`) produce two interceptors over one global.
- **Evidence:** Probe `P6a` — Bugsee installs, another SDK wraps over us, Bugsee uninstalls: `fetch === native ? true`, `other SDK wrapper still installed ? false` (their patch is gone). Probe `P6b` — interceptors A then B, uninstall A then B: after A `current === native ? true` (B's wrapper destroyed); after B `current === native ? false` (the global is left as A's orphaned wrapper). All six `onDeactivate` mutations (`F5`, `X1`, `C1`, `W1`, `S2`, `U1`) were **CAUGHT**, so restoration *is* tested — only the adversarial ordering is not.

### 9. Self-isolation is bypassed when a `Request` carries the sentinel and an `init` with headers is also passed — the SDK would capture its own upload traffic

- **Where:** `packages/capture/src/fetch-interceptor.ts:179-188` (`requestHeaders`): when `init.headers` is present it returns **only** the init headers and never merges or falls back to `input.headers`. That record is what `#isInternal` inspects at `:312`.
- **What:** `fetch(new Request(url, { headers: { 'x-bugsee-internal': '1' } }), { headers: { … } })` loses the sentinel, so the SDK's own request is captured — including a `clone()` + bounded read of the upload's response body.
- **Why it matters:** Not reachable through the shipped transports today (`browser-utils/src/fetch-transport.ts` calls `doFetch(url, init)` with the sentinel in `init.headers`; `node`/`webworker`/`vercel-edge` all merge into `options.headers`), which is why this is SEV2 and not SEV1. It becomes SEV1 the moment (a) a transport is refactored to the `Request` form, or (b) a host-installed `fetch` wrapper that normalizes `(url, init)` → `(new Request(url, init), init)` is installed **above** Bugsee — Next.js and several fetch polyfills do exactly this kind of argument normalization. The resulting loop is amplifying rather than infinite (each upload adds ~3 entries to the next bundle), but it also means the SDK stores its own upload URLs and response bodies.
- **Evidence:** Probe `R2a` — `dispatched = 1`, `CAPTURED urls = ["https://ingest.bugsee.test/upload", ×3]`. Control `R2b` (same `Request`, no `init`) — `CAPTURED urls = []`, correctly skipped. Mutations `F9`/`X5` (disable self-isolation entirely) were both **CAUGHT** (4 and 2 failures), so the mechanism is tested; the header-precedence edge is not.

### 10. WebSocket / EventSource per-instance patches are never reverted — a live connection stays instrumented forever after uninstall

- **Where:** `packages/capture/src/web-socket-interceptor.ts:120-124` (an own `send` property is installed on the instance) and `:104-118` (four listeners), `packages/capture/src/sse-interceptor.ts:111-115` (own `close`) and `:102-109`. `onDeactivate` (`web-socket-interceptor.ts:81-86`, `sse-interceptor.ts:79-84`) restores only the **constructor**.
- **What:** The header comment at `web-socket-interceptor.ts:9-10` presents per-instance wrapping as the safe alternative to prototype mutation, but it makes uninstall structurally incomplete: every connection created while active keeps the SDK's `send`/`close` wrapper and listener set, holding a strong reference to the interceptor and its per-connection `state`, for the object's lifetime. Re-activating the interceptor later resurrects emission from those stale wrappers.
- **Evidence:** Probe `P7a` — after `off()`: `ctor restored ? true`, but `own send prop still wrapped ? true`; the app's `send` still worked (`sends = 1`), so host behavior is intact. Probe `P7b` — same for `close` (`own close prop = true`, `closed = 1`).

### 11. WebTransport: the interceptor attaches rejection handlers to the application's own `ready`/`closed` promises, suppressing the host's unhandled-rejection reporting

- **Where:** `packages/capture/src/web-transport-interceptor.ts:101-104` (`session.ready.then(onOk, onErr)`) and `:105-108` (`session.closed.then(...)`).
- **What:** Attaching an `onRejected` handler marks a promise as handled. An application that constructs a `WebTransport` and never touches `ready` would normally surface an `unhandledrejection` (or terminate a Node process under the ≥15 default) when the session fails; with Bugsee installed that signal disappears. This is an observable change to the host's error-reporting behavior caused purely by observation. Secondarily, the two derived promises are floating (no `void`, no `catch`), so any throw inside the handlers would itself become an unhandled rejection.
- **Evidence:** Probe `P8a` — a session whose `ready` and `closed` both reject: `stages = ["before","error","close"]` with no unhandled rejection reported by the runner, i.e. both rejections were consumed by the SDK.

### 12. Blast radius of the confirmed `runFilter` core defect: on this package's two paths a filter that forgets to `return` silently annihilates 100 % of the stream with **no** diagnostic on any sink

- **Where:** `packages/capture/src/network-provider.ts:94-96` and `packages/capture/src/log-provider.ts:36-40`.
- **What / Why it matters:** Root cause already confirmed in `docs/review/core-B-capture-pipeline.md` SEV1 #1 (`core/src/filters.ts:44-58`); not re-litigated. Reported here because the *manifestation* differs from core's client paths: the resulting `TypeError` is raised inside an `onAny`/`on` listener and is therefore swallowed by `MultiKeyEmitterBase.#dispatch` (`core/src/emitter.ts:88-94`), whose `onListenerError` sink is never wired (core-B SEV2 #4). The host application is **not** broken — but every network/log entry is dropped for the whole session, the filter's own `onError` never fires, and nothing anywhere records that it happened.
- **Evidence:** Probe `R3a` (real `createFilterStore` + real carrier client + real interceptor + real provider, filter body `() => { /* no return */ }`): `hostThrew = undefined | entries captured = 0 | filter onError calls = 0`. Probe `R3b` (log path): `hostThrew = undefined | log entries = 0 | app passthrough = 1 | filter onError = 0` — the app's own `console.log` still worked, and the entire log stream vanished.

## SEV3

### 13. `readBoundedBody`'s byte cap is defeated by a non-`Uint8Array` chunk, and the resulting throw escapes as an unhandled rejection

- **Where:** `packages/capture/src/fetch-interceptor.ts:159-160` (`const chunk = value as Uint8Array; total += chunk.byteLength;`), `:175` (`decodeUtf8(chunks)` sits **outside** the `try` that ends at `:174`), and `:270` (`void readBoundedBody(...).then(...)` — no rejection handler).
- **What:** A stream yielding non-byte chunks makes `chunk.byteLength` `undefined`, so `total` becomes `NaN` and `NaN > maxBytes` is always false — the cap never trips and chunks accumulate until the stream ends. Then `decodeUtf8` (`network-body.ts:88`, `all.set(chunk, offset)`) throws a `RangeError` from outside the guarded region, rejecting `readBoundedBody`'s promise; `:270` attaches no `onRejected`, so it reaches the host runtime.
- **Why SEV3:** a real `Response.body` is always a byte stream, so this is reachable only through a custom `fetchTarget`, a polyfilled/mocked `fetch`, or `new Response(<non-byte ReadableStream>)`.
- **Evidence:** direct reproduction of the `decodeUtf8` body — `string chunk => THROWS: RangeError: Range consisting of offset and length are out of bounds`; `plain array chunk => THROWS: RangeError`; and `total += undefined → NaN`, `NaN > 20480 → false`.

### 14. The console patch does not preserve `fn.length` or `fn.name`

- **Where:** `packages/capture/src/console-interceptor.ts:92` — the replacement is a rest-arg arrow, so `console.log.length` becomes `0` and `console.log.name` becomes `''`.
- **Evidence:** probe `P4c` — original `function log(a, b)` → `patched.length = 0`, `patched.name = ""`. Low impact (libraries rarely feature-detect on console arity), but it is a visible identity change to a host global. The equivalent question for the other five sources is answered correctly: fetch/XHR/WS/SSE/WT all preserve the app-visible return value, `this`-binding and prototype chain (see the matrix below).

### 15. Surviving mutation: the `Content-Length == maxBytes` boundary is untested

- **Where:** `packages/capture/src/fetch-interceptor.ts:139`. Mutation `F1` (`contentLength > maxBytes` → `>=`) **SURVIVED** the full suite. Under the mutant, a response whose `Content-Length` is exactly the cap is wrongly reported `size_too_large` and never read. The sibling in-stream cap at `:161` **is** boundary-tested (`F3` caught, and there is an explicit *"keeps a body exactly at the byte cap"* test at `fetch-interceptor.test.ts:438`); the `Content-Length` fast-skip has the over-cap test (`:449`) but no at-cap test.

### 16. Surviving mutation: the console `this`-binding is untested

- **Where:** `packages/capture/src/console-interceptor.ts:106`. Mutation `C3` (`original.apply(con, args)` → `original(...args)`) **SURVIVED**. V8 tolerates a detached `console.log`, but jsdom's virtual console, several React-Native/Electron console shims and older WebKit do not. The correct binding is deliberate (the `con` capture at `:82`) and unpinned.

### 17. Test theater on the resource-safety property: no test in the package ever constructs a real `Response` or `ReadableStream`

- **Where:** `packages/capture/src/fetch-interceptor.test.ts` — `okResponse()` (`:23-30`) and `responseWith(...)` are hand-rolled object literals; `cancel` is `vi.fn(() => Promise.resolve())` (`:412`) or `cancel: () => Promise.resolve()` (`:506`). A repo-wide grep for `new Response` / `new ReadableStream` across all 17 test files returns **zero** hits.
- **Why it matters:** the test named *"cancels the reader when stopping early on an over-cap body (**releases the tee branch**)"* (`:411`) asserts `cancel` was called once — which is true — while the real consequence of that call is the permanent hang of SEV1 #1. The test at `:567` (*"reads only the clone, never the original response body"*) asserts `originalRead === 0` against a fake `body` getter; with a real `Response`, `clone()` **replaces** `response.body` with a tee branch, so the property being asserted is a property of the fake. (The underlying claim does hold — verified independently in probe `P1c`: real `Response`, `bodyUsed === false`, `body.locked === false`, app read all 50 000 bytes — but the suite does not establish it.) One `describe` block using the platform `Response` would have caught SEV1 #1 on day one.

### 18. Unguarded timer callback in the system-traces provider

- **Where:** `packages/capture/src/system-traces-provider.ts:61` (`setInterval(() => this.#emit(), …)`) and `:69-74`. A throw from the injected `sample()` (`:71`) or `now()` (`:70`) inside the interval callback is an uncaught exception in a timer, which terminates a Node process. The same throw on the initial synchronous sample (`:60`) propagates into `provider.start()` and, via the unguarded `capture-coordinator.ts:69-71` loop, strands every later provider. Both seams are platform-injected, so this is defensive-only today.

### 19. No frame-rate bound on WebSocket message capture

- **Where:** `packages/capture/src/web-socket-interceptor.ts:105-107` and `:121-124` — one `NetworkEvent` per frame, in both directions, with no sampling or coalescing. A high-frequency socket (market data, multiplayer state sync, a collaborative editor) will dominate the capture ring and evict every other entry type. Android's parity target throttles nothing here either, so this is a design note rather than a divergence — but it is the one capture source with no natural rate bound.

## Inherited core-defect blast radius

**`InterceptorBase` sets `#active` before `onActivate()` (`core/src/interceptor-base.ts:46`).** Every source in this package writes a runtime global inside `onActivate`, so **all six can throw**:

| Source | `onActivate` write | Realistic throw |
|---|---|---|
| fetch | `fetch-interceptor.ts:298` — `globalThis.fetch = wrapper` | frozen/non-writable/getter-only global (SES, lockdown, hardened realm, a competing SDK's non-configurable accessor) |
| xhr | `xhr-interceptor.ts:136-138` — three prototype writes | frozen `XMLHttpRequest.prototype` |
| websocket | `web-socket-interceptor.ts:72` `class extends original`, `:78` assignment | frozen global; **also** a non-constructor `globalThis.WebSocket` makes the `extends` clause itself throw |
| sse | `sse-interceptor.ts:70`, `:76` | same |
| webtransport | `web-transport-interceptor.ts:69`, `:74` | same |
| console | `console-interceptor.ts:92` — `console[method] = wrapper` | `Object.freeze(console)`; some Electron/RN console shims define read-only methods |
| **network (umbrella)** | `network-interceptor.ts:47` — subscribes to each leaf, which transitively activates it | **inherits every leaf's failure and multiplies it** — SEV1 #6 |

The umbrella is what turns a bounded core defect into a session-wide one: `#offs` is assigned only after the whole `map` completes (`:47`), so a mid-map throw both leaks the already-installed leaf patches *and* leaves the umbrella permanently "active" with nothing wired. Because `capture-coordinator.ts:69-71` is also unguarded and `network` is provider #2 of 5 (browser) / #2 of 4 (node), the practical outcome is: **console logs only, launch reports success**. Empirically confirmed (`P3a`, `P3b`, `R4a`).

**`runFilter` never normalizes a falsy return (`core/src/filters.ts:53`).** Two emit paths in this package hit it — `network-provider.ts:94-96` and `log-provider.ts:36-40`. Neither reaches the host application (both run inside emitter listeners, isolated at `core/src/emitter.ts:88-94`); both silently drop 100 % of their stream with no sink firing. Detail and evidence under SEV2 #12. The remaining emit paths in this package (`system-events-provider.ts:40`, `user-events-provider.ts:41`, `system-traces-provider.ts:72`) do **not** consult filters at all, so they are unaffected — and, correspondingly, are not user-redactable.

## Protocol-conversion siting

**`logLevelToWire` — NOT this package's job (it is a contributor, not the site).** `console-interceptor.ts:24-30` mints the string level names (`'info' | 'debug' | 'warning' | 'error'`) and emits them at `:98`, and `log-provider.ts:38`/`:41` forwards the `LogEvent` verbatim. **`NetworkStage` websocket/`event` encoding — YES, this package is exactly where it should have been emitted.** The Android-canonical shape (`type: "websocket"` + a separate `event: "create"|"open"|"send"|"message"|"close"|"error"`, per `docs/design/sdk-design.md` §8.7) is produced nowhere else. ## Checked and found clean

- **The fetch clone design does preserve the host's response.** Against a **real** `Response`: `bodyUsed === false` and `body.locked === false` immediately after the call (probe `P1c`); the app read all 50 000 bytes; with a 16-byte cap against a 200 000-byte body the app still read all 200 000 (probe `P1b`/`R5a`). The `clone()` failure paths are correct and tested — `noClone`, `clone()` throws, and body-already-used all skip the amendment rather than risking the app's stream (`fetch-interceptor.ts:258-266`; tests `:545`, `:557`).
- **Backpressure coupling is bounded.** The tee lets the SDK's eager read defeat the app's backpressure, but only until `maxBodyBytes`, after which our branch is cancelled and the tee resumes respecting the app's branch alone. Probe `P1d` — the app cancelled its body immediately; the source was pulled 23 × 1 KB (the 20 KB cap) and then stopped. Extra network read is bounded by the cap, by construction.
- **The mutation battery is convincing: 37 of 39 caught, 0 invalid.** Caught include every body-policy mutation (`F2`, `F3`, `F4`, `F7`, `X2`, `N1`, `N2`, `N3`, `N4`, `P1`, `P4`, `P5`), every sanitizer fail-open mutation (`P2` header redaction → no-op, `P3` body redaction → no-op, `P6` default-sanitizer forced off), both self-isolation mutations (`F9` 4 failures, `X5` 2), both decorator-wire mutations (`F6` 3 failures, `X4`), all six un-patch mutations (`F5`, `X1`, `C1`, `W1`, `S2`, `U1`), the case-insensitivity mutations (`N5`, `N6`), `decodeUtf8` offset (`N7`), the console re-entrancy guard (`C2`), and the frame-direction flip (`W2`). Controls `F8`, `X3`, `C4`, `P7`, `W3`, `S1` all bit. Only `F1` and `C3` survived (SEV3 #15, #16).
- **Runtime portability is genuinely absolute.** Zero `node:*`, `fs`, `http`, `path` imports; no unconditional DOM reference. Every runtime global is reached through a lazy getter closure (`fetch-interceptor.ts:36-41`, `xhr-interceptor.ts:49-51`, `web-socket-interceptor.ts:26-31`, `sse-interceptor.ts:25-30`, `web-transport-interceptor.ts:24-29`, `console-interceptor.ts:20-21`, `network-body.ts:38`/`:77`, `traceparent.ts:95-97`/`:126`), so **nothing** is evaluated at import time and every source self-skips cleanly when its global is absent (`fetch-interceptor.ts:294-296`, `xhr-interceptor.ts:127-129`, `web-socket-interceptor.ts:67-69`, `sse-interceptor.ts:65-67`, `web-transport-interceptor.ts:64-66`, `console-interceptor.ts:83-85`, plus the per-method `typeof original !== 'function'` skip at `console-interceptor.ts:88-90`). The only top-level `globalThis` touch is the alias at `system-traces-provider.ts:18`, which reads no property. Import-time safety verified on the DOM-less `node` vitest environment for all 17 modules.
- **No unbounded id-keyed map anywhere.** The classic "map keyed by request id whose completion never arrives" leak does not exist here: fetch keeps per-request state in the wrapper closure only, XHR uses a `WeakMap` keyed by the instance (`xhr-interceptor.ts:100`), and WS/SSE/WT keep per-connection state in listener closures collected with the object. The two real leaks are elsewhere (SEV1 #1's suspended frames and SEV2 #7's listener stacking).
- **`#gateBody` has no bypass.** Every source funnels through the umbrella (`install-network-capture.ts:90`) into the single `onAny` at `network-provider.ts:87`, and `:91` gates *before* the filter/sanitizer XOR — including the fetch body amendment (`fetch-interceptor.ts:274-288`), which was the most likely place for a second path. Verified in probe `P9b` (the amendment entry is gated and sanitized like any other). Mutation `P4` (skip the gate) was caught with 5 failures.
- **Sanitization fails closed.** A throwing `sanitizeHeaders`/`sanitizeBody` propagates out of the `onAny` listener into `#dispatch`, which drops the event — the unsanitized entry is never captured. `sanitize()` (`network-provider.ts:31-45`) is also correctly non-mutating: it builds a new event rather than writing back onto the emitter's shared payload, so later subscribers see the raw event (the SEV2 #6 aliasing hazard core-B raised at the `runFilter` layer does **not** apply to the default-sanitizer branch).
- **Order of operations matches Android.** `#gateBody` → (user filter XOR default sanitizer) → capture, exactly as documented at `network-provider.ts:62-64` and `:88-90`. The XOR (a user network filter *replaces* the built-in PII sanitizer) is the deliberate Android rule, not a defect — but it is worth an explicit line in the public docs, because a user adding a filter merely to drop `/health` requests silently forfeits `Authorization`/`Cookie` redaction (`network-provider.ts:94-97`).
- **The decorator seam is observe-only by default.** With no decorator registered, `run()` returns `undefined` and `effectiveInit === init` by reference — verified by the test at `fetch-interceptor.test.ts:639` (`expect(received()?.init).toBe(init)`) and by mutation `D1` being caught. `traceparent.ts` is correctly conservative: cross-origin propagation requires an explicit allowlist (`:130-139`), an upstream `traceparent` is never overridden (`:142`), and `defaultResolveOrigin` swallows parse failures into "cross-origin" (`:101-105`) — the safe direction.
- **`request.json`-adjacent metadata is honest.** When a decorator adds headers, the emitted event carries the same headers that go on the wire (`fetch-interceptor.ts:322`, `xhr-interceptor.ts:197-200`), so capture never reports a request shape the app did not send. Mutations `F6` and `X4` (apply to capture but not the wire) were both caught.
