# Adversarial review — @bugsee/browser-utils

**Reviewed:** 2026-07-26 · **Scope:** packages/browser-utils (impl 1199 LOC across 10 files, tests 2041 LOC across 9 files, 123 tests, 100% stmt/branch/fn/line)
**Verdict:** The package is well-factored and its test suite is genuinely strong — 9 of 10 injected mutations were caught, including every mutation in the Web Locks claim protocol, the snapshot count bound, the pin refcount, and the prefix-stripping views. The multi-tab coexistence design is sound and *strictly better* than the node twin: `navigator.locks` with `ifAvailable` is an atomic claim with no staleness window, and the slice-5 capture-sweep hazard is genuinely closed (verified by construction and by mutation — a live sibling's data is provably never read, recovered, or swept). The defects are concentrated in the **substrate-divergence** the package introduced when it re-implemented core's chunk backend over async IndexedDB: the file backend's torn-record tolerance, its transaction-completion semantics, and its snapshot pin protocol were each **dropped or weakened** in the IDB port, and none of the drops are tested. Three are SEV1: one corrupt IDB record permanently destroys a whole generation's recovery (and the poisoned data is then never freed), the write queue has **zero** back-pressure (20,000 entries accepted with 1 write in flight, ~200 MB retained — reproduced), and orphaned capture data is never reclaimed when Web Locks is unavailable or `recover:false`, which grows origin quota without bound and can break the host application's own storage. Separately, the "the browser flushes via the pipeline / pagehide" claim written in two places in `@bugsee/browser` describes a flush that **does not exist anywhere in the codebase**. Auth-token hygiene and the `X-Bugsee-Internal` self-capture isolation are clean.

All six reproductions below were run against the real code with `fake-indexeddb`; every source file touched was restored from a `cp` backup and `git status --short packages/` is empty.

## SEV1

### 1. ONE corrupt IndexedDB record permanently destroys the whole generation's recovery — and the poisoned data is then never freed

- **Where:** `packages/browser-utils/src/idb-chunk-backend.ts:216` (`dec<StoredData>(...)` inside `readAll`) and `:148` (`dec<StoredMeta>(bytes)` inside `readMetas`). `dec` is an unguarded `JSON.parse` (`:60`).
- **What:** Both the data-envelope parse and the meta parse are bare `JSON.parse` calls inside a loop with no per-record guard. A single unparseable value rejects the entire `snapshot().drainAll()` / `listParts()`.
- **Why it matters:** This is the exact failure class core explicitly designed against. `packages/core/src/capture-drain.ts:24-30` carries the comment *"Skip it; NEVER let one bad record poison the whole generation's recovery (which would keep the marker + chunks and repeat the failure on every launch — a permanent loss)"* — and core's file backend implements it (`packages/core/src/file-chunk-backend.ts:66-69` try/catch on meta, `:128` and `:133` `continue` on a torn line). The IDB backend is the unguarded outlier. Worse, the guard in `drainReified` sits at the *inner* `entry.deserialize` layer; the IDB backend's **outer envelope** parse runs earlier, inside `drainAll()`, so it bypasses the guard entirely — `drainReified` has `try { … } finally { release() }` with **no `catch`**, so the rejection propagates.
- **Permanence (traced):** `capture-recovery.ts:61-88` catches per generation → `onError`, markers **not** removed → `stillPending` at `:94` contains that generation → the sweep at `:96-103` **keeps** it. Next launch: identical failure. Forever. The generation is a dead-sibling prefix, so it also accumulates in IndexedDB permanently.
- **Evidence (REPRO A, reproduced):** 3 records written, envelope for `seq 1` overwritten with `{"t":0,"s":"trunc`; `snapshot([{count:3}])` → **rejects** `SyntaxError: Unterminated string in JSON at position 17`. `good-0` and `good-2` — untouched, intact — are lost with it.
  **CONTROL (same run):** core's `createFileChunkBackend` fed an equivalent torn line returned `['good-0','good-2']` — survivors kept. Confirmed asymmetry, same commit, same test file.
- **Evidence (REPRO B, reproduced):** one corrupt meta value for chunk 0 → `listParts(5)` **rejects** for the whole generation (`SyntaxError: Expected property name or '}'`), taking chunk 1's perfectly good meta with it. Core's `readMeta` (`file-chunk-backend.ts:66-69`) falls back to a derived default instead.
- **Reachable triggers:** (a) `getAll`/`getAllKeys` returning different-length arrays — the code does `values[index] as Uint8Array` at `idb.ts:157` and `:77` with a cast that hides the hole; `TextDecoder().decode(undefined)` → `''` → `JSON.parse('')` throws, same total loss; (b) storage-layer corruption in the browser's IDB backing store; (c) envelope-schema drift across SDK versions on the **dead-sibling** recovery path, which by construction reads data a *different* build wrote. Regardless of trigger frequency, the blast radius is unbounded and the recovery is unrecoverable, which is what makes it SEV1.

### 2. The durable write queue has zero back-pressure — unbounded memory on a stalled IDB, and one `onError` per captured entry on a failing one

- **Where:** `packages/browser-utils/src/idb-chunk-backend.ts:94-96` (`enqueue`: `queue = queue.then(op).catch(onError)` — no depth counter, no cap, no drop policy) driven from `:175` (`appendEntry`, one enqueue per captured entry).
- **What:** `appendEntry` is sync-issue/async-complete and returns unconditionally. Every entry allocates a closure retaining its serialized payload and chains it onto a single serial promise queue. There is no signal back to the capture path when the queue is not draining.
- **Why it matters:** This is the direct browser analogue of the node-utils SEV2 (`batched-fs-chunk-storage.ts` ENOSPC → unbounded memory). Core's ring eviction cannot rescue it: `removePart`/`removeGeneration` enqueue their `deletePrefix` at the **tail** of the same queue (`:107-108`, `:198-199`), so eviction can never run ahead of the backlog. Quota pressure, private/incognito storage, and a busy IDB thread all produce exactly this stall.
- **Evidence (REPRO E, reproduced):** stalled store, 20,000 entries × 10 KB appended → **`pending.length === 1`**. 20,000 entries accepted, one IDB write actually started, `≈200 MB` of payload retained live in the pending promise chain, with `add()` still returning success to every caller.
- **Evidence (REPRO D, reproduced):** store rejecting every `put` with `QuotaExceededError` → **`puts attempted = 5001`, `onError calls = 5001`**. No circuit breaker, no degradation to memory-only, no eviction of the SDK's own oldest data to make room. Exactly the node twin's "one failing syscall + one `onError` per captured entry".
- **Amplification into a page-hanging livelock:** `onError` is the *host-supplied* sink (`launch.ts` threads `options.onError` straight into `createIdbChunkCaptureStore` at `packages/browser/src/launch.ts:367-370`, documented as "Internal-error sink"). If the host implements it as `onError: e => console.error(e)` — the obvious implementation — then: failed put → `onError` → `console.error` → the console interceptor captures it → `add()` → `appendEntry` → enqueue → fails → `onError` → … The console interceptor's re-entrancy guard does **not** stop this: `packages/capture/src/console-interceptor.ts:71` `#capturing` is a *synchronous* flag set/cleared in a `try/finally` within one turn (`:94-105`), while `onError` arrives from a promise rejection in a **later microtask** with the flag already `false`. Gain is exactly 1 per iteration, so it is a self-sustaining loop that never terminates for the life of the page: permanent console spam, permanent failing IDB writes, permanent CPU.
- **The default is the other half of the hazard:** with `onError` unset (the default — `idb-chunk-backend.ts:89` `?? (() => {})`), quota exhaustion means capture dies **silently and permanently** with zero signal to anyone, while `snapshot()` keeps returning short reads (`:215` bounds by `records.length`) and reports upload truncated with no indication they are incomplete.

### 3. Orphaned capture data is never reclaimed when Web Locks is unavailable or `recover:false` — unbounded origin-quota growth that can break the host application

- **Where:** `packages/browser-utils/src/web-lock-liveness.ts:47` (`recoverIfDead: () => Promise.resolve()` in the degraded branch) and `coexistence.ts:176-196` (the only path that ever touches a sibling's data), wired at `packages/browser/src/launch.ts:299-306` and `:493-514`.
- **What:** Reclamation of a dead instance's IndexedDB data happens **exclusively** inside `recoverIfDead(…)`'s callback, via core's sweep (`capture-recovery.ts:96-103`). Two configurations disable that callback entirely while leaving the *write* path fully enabled:
  1. **`navigator.locks` unavailable** → `createWebLockLiveness(undefined)` returns the degraded object whose `recoverIfDead` resolves immediately without ever invoking `fn`. Nothing is recovered and, critically, **nothing is swept**.
  2. **`recover: false` with `persist: true`** → `recoverEnabled` is false (`launch.ts:300`), so `recoverReportsForViews` is omitted from the `recoverDeadSiblings` options — but `durableCapture` is still `true` (`:299`), so `captureShared` is created and **written to** for the whole session. Dead siblings' capture prefixes are then never read and never deleted.
- **Why it matters:** Each launch mints a fresh `instanceId` (`instance-coexistence.ts:11`) and writes up to `maxDataSize` (default **10 MB**, `launch.ts:348`) of capture chunks under it. With no reclamation path, every page load permanently orphans another prefix. IndexedDB quota is **origin-scoped and shared with the host application** — ten navigations is ~100 MB of dead SDK data, after which the *host page's own* IDB writes start failing with `QuotaExceededError`. That is a direct violation of the binding "interceptors must not alter app behavior" principle, and the SDK provides no eviction of its own orphans to escape it.
- **Reachability of branch 1 is not exotic:** `navigator.locks` is `[SecureContext]` — it is `undefined` on any plain-`http://` origin, where IndexedDB still works fine. It is also absent on Safari < 15.4 and in a number of embedded webviews. `persist: true` is the documented setting for "guaranteed crash delivery", i.e. the one users are steered toward.
- **The existing test asserts the leak as correct:** `coexistence.test.ts:248` — *"degrades when Web Locks is unavailable: still persists locally, recovers no sibling"* — verifies that data keeps being written and never reclaimed, without any assertion (or comment) about the resulting unbounded growth.

## SEV2

### 4. Write paths resolve on **request success**, never on transaction completion — a commit-time quota failure silently loses the write with no `onError`

- **Where:** `packages/browser-utils/src/idb.ts:140-141` (keyed `put`), `:60-61` (blob `run`, used by `put`/`remove`), `:172-173` (`keys`), `:185-186` (`deletePrefix`) — all resolve/reject from `request.onsuccess`/`request.onerror` only. None wires `transaction.oncomplete` or `transaction.onabort`.
- **What / why it matters:** `request.onsuccess` fires *before* the transaction commits. A failure at commit time — which is precisely how quota enforcement and disk errors surface in real browsers — aborts the transaction **after** the promise has already resolved. The queue advances, `onError` is never called, and the entry is silently gone. `snapshot()` then reads fewer records than `count` and truncates the report with no signal (`idb-chunk-backend.ts:215`).
- **Evidence of the inconsistency inside the same file:** the *read* paths do it correctly — `loadAll` uses `transaction.oncomplete`/`transaction.onerror` (`idb.ts:74-80`) and `readPrefix` does the same (`:154-160`). Only the write paths skip it.
- **Untestable with the current harness:** `fake-indexeddb` never fails a commit, so no test can distinguish the two designs.

### 5. No flush-on-exit exists at all, and the transport cannot survive unload — the documented pagehide flush is fiction

- **Where:** `packages/browser-utils/src/fetch-transport.ts:26` — `const init: RequestInit = { method, headers, signal }`; no `keepalive`, no `sendBeacon` path, no unload-aware mode.
- **What:** The browser tier's only exit signal is `pagehide` (`packages/browser/src/system-events.ts:70`), and its handler (`:39-44`) does nothing but `emit` a `process_exiting` **capture entry**. `grep -rn "flush" packages/browser/src` returns **comments only** — there is no flush call anywhere in the package. Yet `packages/browser/src/detection-providers.ts:17` and `packages/browser/src/launch.ts:73` both assert *"the browser flushes via the pipeline / pagehide"*.
- **Why it matters:** With the default `persist: false` there is **no** durable bundle store (`launch.ts:310-320`: no `bundleStore` → no `durable` → the raw pipeline), so a report generated in the last moments before unload — a JS error thrown during a link click, the single most common real-world case — has its in-flight `fetch` killed with the document and is lost outright. This is the browser analogue of the node twin's "flush-on-exit does not run on SIGTERM", and here it is worse: node at least *has* a handler.
- **Note on the obvious fix:** adding `keepalive` is not sufficient — browsers cap total in-flight keepalive request bodies at **64 KiB per fetch group**, and bundles are bounded by `maxDataSize` (default 10 MB). The only correct answer for large bundles is the durable queue, which is off by default. Whichever way this is resolved, the two comments claiming a flush exists must go.
- **What is lost on a backgrounded-then-OS-killed tab (the common mobile case):** everything not already committed to IDB — which, per finding #2, can be the entire pending queue. Web Locks *does* handle this case correctly for the **recovery** side: the realm dies, the lock auto-releases, and the next launch on that origin recovers the data as a dead sibling (when `persist` and `recover` are both on).

### 6. `dbPromise` is cached forever — including a rejection and a force-closed connection; no `onblocked`, no `onversionchange`, no reopen

- **Where:** `packages/browser-utils/src/idb.ts:34-49` (blob store) and `:112-125` (keyed store) — `dbPromise` is memoised on first `open()` and never invalidated or retried. `grep` for `onblocked|onversionchange|\.close()` across `packages/browser-utils/src` returns **nothing**.
- **What / why it matters:** Three consequences. (a) If the initial `open` rejects, the rejected promise is cached and *every* subsequent operation for the session rejects — durability is permanently dead with no retry, even if the cause was transient. (b) If the connection is force-closed by the browser (storage eviction, "clear site data", a `versionchange` from another context), `db.transaction(...)` throws `InvalidStateError` from then on, forever — the store never reopens. (c) Because `db.onversionchange` is never handled and the connection is never closed, **this SDK will indefinitely block any future attempt to upgrade or delete its own database** — including a future SDK version bumping past `version: 1` (hard-coded at `:38` and `:116`), which would hang on `onblocked` with no handler and no timeout.
- **Untested:** no test in the package exercises `onblocked`, `versionchange`, `onabort`, or a post-close reopen (keyword scan: zero hits for all four).

### 7. Coexistence discovery materialises every instance's bundle and marker **values** just to enumerate keys — then reads them a second time

- **Where:** `packages/browser-utils/src/coexistence.ts:161` and `:165` — `blob.loadAll().then((es) => es.map(([k]) => k))`. The values are read from IndexedDB, structured-clone-deserialized, and immediately discarded.
- **What / why it matters:** `AsyncBlobStore` (`idb.ts:7-14`) has no `keys()` method, so key enumeration must go through `loadAll()`. The capture store *does* have a cheap `keys()` and the code uses it (`:169`) with the comment *"a keys-only scan — no values"* — but the comment two lines above at `:142-144` describes the blob loads as **"cheap full loads"**, which is exactly backwards. This runs at every launch, on the main thread, over every instance's bundles. `recoverSiblingBundleQueue` then loads the same dead sibling's bundles **again** (`recover-dead-instances.ts:23`).
- **Evidence (REPRO F, reproduced):** enumerating **2 keys** materialised **2,000,000 value bytes**.
- **Compounding:** `Promise.all` over all dead siblings (`coexistence.ts:176`) runs every sibling's recovery — each loading all its bundles into RAM and uploading — with **unbounded concurrency**.

### 8. The durable bundle queue is fully RAM-resident and unbounded

- **Where:** `packages/browser-utils/src/idb-bundle-store.ts:26` (`const mirror = new Map<string, Uint8Array>()`), `:42` (`put` keeps bytes in the mirror), `:30-36` (hydration loads every persisted bundle into it at open).
- **What / why it matters:** The sync-`BundleStore`-over-async-IDB adapter keeps **every undelivered bundle's full bytes in memory** for the whole session, in addition to IndexedDB. Bundles are bounded only by `maxDataSize` (10 MB default) each, and a bundle is removed only on confirmed delivery. An offline or endpoint-down period accumulates them without bound in both RAM and IDB. At launch, hydration deserializes all of them synchronously on the main thread. This is the browser analogue of the node twin's "on-disk bundle queue has no retention bound" — with RAM residency added on top. There is no count cap, no byte cap, and no age-based eviction anywhere in the file.

## SEV3

### 9. `removeGeneration` bypasses the snapshot pin protocol that `removePart` honours

- **Where:** `packages/browser-utils/src/idb-chunk-backend.ts:197-200` — `removeGeneration` enqueues `deletePrefix` unconditionally, ignoring `pins` and `deferredDelete`, which `removePart` correctly consults at `:190-194`.
- **Evidence (REPRO C, reproduced):** with a live snapshot pinning a part, `removeGeneration(5)` → the snapshot yields **`[]`** (data deleted mid-read). The control in the same test: `removePart` under an identical pin → **`['pinned']`**, correctly deferred.
- **Reachability today: none.** `chunk-capture-store.ts:108-113` `clear()` calls it, and `capture-aggregator.ts:76-78` exposes `clear()`, but `grep` finds **no caller** of the aggregator's `clear()` anywhere in the shipped code. `capture-recovery.ts:102` calls it only in the sweep, after `drainReified`'s `finally` has released every snapshot. Filed as a latent contract violation, not a live bug — the substrate divergence matters because the file backend reads **eagerly** at `snapshot()` (`file-chunk-backend.ts:120-138`), which makes clear-after-snapshot inherently safe there, while the IDB backend defers the read and depends entirely on the pin protocol it then only half-implements.

### 10. Surviving mutation: `createCoexistence`'s inline self-exclusion is untested, and it duplicates a dead exported function

- **Where:** `packages/browser-utils/src/coexistence.ts:150` — `split.instanceId !== instanceId`.
- **Mutation (M3, SURVIVED):** replacing `split !== undefined && split.instanceId !== instanceId` with `split !== undefined` — i.e. adding **self** to the dead-sibling recovery set — leaves all 14 `coexistence.test.ts` tests passing. No test asserts self-exclusion in this code path.
- **Why it matters:** self-exclusion is normally redundant (self holds its own lock, so `ifAvailable` yields `null`) — but `holdSelf` **deliberately swallows a failed lock request** (`web-lock-liveness.ts:58-60`, with the comment "this instance simply won't be lock-protected"). In that degraded state the `!== instanceId` check is the *only* thing preventing the instance from recovering, re-uploading, and **deleting its own live session data** mid-flight. That is precisely the branch with no test.
- **Related:** `recoverDeadInstances` (`recover-dead-instances.ts:71-107`) is exported from the public index (`index.ts:46`) and has **zero production consumers** — `grep` outside `packages/browser-utils/src` returns nothing. `createCoexistence` re-implements its discovery-and-claim loop inline instead of calling it. `recover-dead-instances.test.ts:86` *does* test self-exclusion — for the copy that nothing uses. Two implementations of one invariant, one tested, the live one not.

### 11. The IDB injection seam is incomplete: `IDBKeyRange` is taken from the ambient global

- **Where:** `packages/browser-utils/src/idb.ts:129` — `IDBKeyRange.bound(prefix, \`${prefix}￿\`)`, a bare global, while `IdbBlobStoreOptions.indexedDB` (`:22`) makes the factory injectable.
- **Why it matters:** injecting `{ indexedDB: new IDBFactory() }` yields a **mixed** environment — ranges from one implementation applied to another's store. Every test file in the package works around this by also importing `'fake-indexeddb/auto'` to patch the global; a real embedder injecting an alternate implementation without that side-effect import gets undefined behaviour. `IDBKeyRange` should ride the same seam.

### 12. The raw `fetchTransport` is exported without the `X-Bugsee-Internal` sentinel

- **Where:** `packages/browser-utils/src/index.ts:11` exports `fetchTransport` (`fetch-transport.ts:56`), which sends no sentinel header.
- **Why it matters:** the self-capture isolation is applied by each platform's launch wrapper independently (`packages/browser/src/launch.ts:246-254`, `packages/webworker/src/launch.ts:151-155`, `packages/vercel-edge/src/launch.ts:121-125` — three copies of the same five lines). Anything wiring the exported transport directly re-opens the feedback loop. The header belongs in the transport, or the raw one should not be public. **The shipped composition is correct** — see the self-capture audit below.

### 13. `hashToken` is a 32-bit FNV-1a — a collision cross-wires two projects on one origin

- **Where:** `packages/browser-utils/src/instance-coexistence.ts:16-23`; consumed by `coexistenceDatabaseName`/`captureDatabaseName`/`markerDatabaseName`/`instanceLockName` (`:26-36`).
- **Why it matters:** two colliding app tokens on one origin share one database. `recoverSiblingBundleQueue` (`coexistence.ts:181`) then re-uploads project A's persisted bundle through **project B's** pipeline (built with B's `appToken`). `coexistence.test.ts:197` asserts *"NEVER recovers a different app token's bundles"* — true only absent a collision, which the test cannot exercise. Practically negligible (one or two tokens per origin), but the "wrong-project guard" comment at `:14-15` overstates the guarantee.

### 14. Main-thread and allocation hygiene

- **Where:** `idb-chunk-backend.ts:58-60` — `new TextEncoder()` / `new TextDecoder()` allocated **per record**, on the hot capture path; hoisting them to module scope is free. `:210-220` — `readAll` runs a synchronous `JSON.parse` loop over an entire part's records at report-assembly time on the main thread (it yields between parts, not within one). `idb.ts:152-153` — `getAll()` materialises a whole part's values in one shot.

## Durability audit — `add(entry)` → bytes in IndexedDB

The B5b in-memory-mirror design was **partly** superseded, not fully. Two different designs coexist in this package:

1. **Capture chunks — durable-as-captured (the binding rule), correctly shaped:** `CaptureStore.add` → `chunk-capture-store.ts:74-81` → `backend.appendEntry` (`idb-chunk-backend.ts:170-177`). The entry is **not** buffered in RAM as part of an open chunk; only chunk *metadata* lives in memory (`openStarts`, `seqByChunk`, and the `IndexedPart` list in core). One `store.put` is issued per entry. This is the correct shape and matches the rule.
2. **Bundle queue and report markers — still the in-memory mirror:** `idb-bundle-store.ts:26` and `idb-report-marker-store.ts:32` both keep a full `Map` mirror serving the sync core contract, writing through asynchronously. That is a legitimate adaptation (core's `BundleStore`/`ReportMarkerStore` contracts are synchronous), but it means finding #8 applies: the mirror is unbounded.

**Is the entry durable before `add()` returns? No — and the gap is much larger than documented.** `appendEntry` returns synchronously after `enqueue`, before `store.put` is even *called*, let alone committed. The header comment at `:24` claims a ≤1-entry loss window; the real window is the full queue depth, which REPRO E drove to 19,999 with a single write in flight. A synchronous burst (a tight `console.log` loop, a network-heavy page, a render storm) enqueues N entries in one task while at most one IDB transaction is open.

**Commit timing (the specific hazard the mandate asks about): confirmed present.** `put` resolves on `request.onsuccess` (`idb.ts:140-141`, `:60-61`), which fires **before** the transaction commits. The write paths never observe `transaction.oncomplete`/`onabort`, so a commit-time abort — how quota enforcement actually surfaces — silently discards a write the queue already treated as successful. The *read* paths in the same file do use `transaction.oncomplete` (`:74-80`, `:154-160`), so this is an internal inconsistency, not a considered design choice. See SEV2 #4.

**What is lost at the worst moment (tab crash / OOM kill / forced navigation):** every entry still in the queue — bounded only by burst rate and IDB latency, not by 1. Plus, if the crash lands between `request.onsuccess` and commit, entries the SDK believed durable. On recovery the meta record says `n` entries but fewer data records exist; `snapshot` silently truncates at `records.length` (`idb-chunk-backend.ts:215`) and the report uploads short with no indication it is incomplete.

## Multi-tab coexistence race analysis

**The slice-5 capture-sweep hazard is genuinely closed — verified, not trusted.** Three independent mechanisms, each confirmed:
1. Every durable store is a per-instance **prefixed view** (`instance-coexistence.ts:51-92`), and `createIdbChunkBackend`'s `cleanOtherGenerations` sweep operates on that view (`idb-chunk-backend.ts:124-139` → `store.readPrefix('m/')` → `shared.readPrefix('<selfId>/m/')`). A fresh `instanceId` per launch means self's namespace is empty, so the clean-on-init is a structural no-op and **cannot reach another tab's data**. Mutation M11 (drop the prefix strip in `createPrefixedKeyedStore.readPrefix`) was caught.
2. Cross-instance access happens **only** inside `recoverIfDead` (`coexistence.ts:179`), which uses `ifAvailable: true` — an atomic test-and-claim. Mutations M1 (`lock !== null` → `=== null`) and M2 (drop `ifAvailable`) were both caught by `web-lock-liveness.test.ts`.
3. Self holds its lock for the realm's lifetime (`coexistence.ts:129-131`). Mutation M9 (never call `holdSelf`) was caught by three tests.

**Claim race between two tabs: none.** `LockManager.request` with `ifAvailable` is atomic per spec — exactly one contender receives a non-`null` lock, the other receives `null` and skips. The claim is held for the *entire* recovery (`web-lock-liveness.ts:63-69` awaits `fn()` inside the callback), so there is no discovery-to-claim window of the kind the node twin has with `process.kill(pid,0)` + heartbeat staleness. **This is strictly better than the node design** and deserves to be recorded as such.

**Startup window (analysed, narrow, not filed):** `holdSelf` is issued asynchronously (`web-lock-liveness.ts:58` `void locks.request(...)`) while `createCoexistence` returns synchronously. In principle a peer could claim self's lock before it is granted. In practice self has written nothing at that point — its first key requires an IDB `open` (multiple tasks) whereas an uncontended lock grant is one task — and a peer cannot discover an instance id that has no keys. Not filed.

**bfcache:** a bfcached realm is alive, so its lock is retained and peers correctly skip it; on restore it still owns its prefix. This is the correct outcome **if** the browser retains Web Locks across bfcache. I could not verify that behaviour without a real browser, and it is consequential in the other direction: if a browser releases locks on bfcache entry, a peer would claim a *bfcached-but-live* tab's prefix and recover-and-delete data that tab still owns, producing loss on restore. Listed under untested failure modes; it is not assertable from this repo.

**Backgrounded/throttled tab holding a lock forever:** correct by design — a throttled tab is still live and may still hold data; its lock is released the instant the realm dies. No timeout is needed and none should be added.

**`navigator.locks` unavailable:** degrades to *no* cross-instance recovery **and** no reclamation — see SEV1 #3. `navigator.locks` is `[SecureContext]`, so this covers every plain-`http://` origin, not just old browsers.

**Lock and database naming — no host collision:** `bugsee/<tokenHash>/<instanceId>` (`instance-coexistence.ts:35-36`) and `bugsee-<hash>` / `bugsee-capture-<hash>` / `bugsee-markers-<hash>` (`:26-32`). All namespaced; a host collision would require the host to use the `bugsee` prefix deliberately. Clean.

## HTTP transport audit

- **Auth-token hygiene: clean.** The app token travels in the `x-app-token` **header** and a JSON body (`core/src/bugsee-api.ts:41,69`) — never in a URL. `fetch-transport.ts` performs no logging of any kind. The timeout message at `:46` embeds `url` only, which carries no credential. Verified.
- **`X-Bugsee-Internal` self-capture isolation: clean in the shipped composition.** `packages/browser/src/launch.ts:246-254` wraps *the* transport service, and both `createBugseeApi` and `createBundleUploader` consume the wrapped one (`:283-286`). The fetch and xhr interceptors default `isInternal` to a case-insensitive header check (`capture/src/fetch-interceptor.ts:190-192,233,312`; `xhr-interceptor.ts:66,113,183`). No feedback loop. Caveat filed as SEV3 #12 (the raw export, and three hand-copied wrappers).
- **Timeout/abort:** correct — `AbortController` + `setTimeout`, cleared in `finally` (`:24,49-51`), and the timer intentionally stays armed across `response.arrayBuffer()` so the body read is covered. `signal.aborted` distinguishes a timeout from a genuine network error (`:45-48`); mutation M8 was caught.
- **CORS / credentials:** no `credentials` is set, so fetch's `same-origin` default applies and no cookies are sent cross-origin to the collector. Correct and intentional-looking, though undocumented.
- **Retry:** the transport performs none; retry is core's. No double-retry.
- **`keepalive`:** absent — see SEV2 #5.

## Untested real-browser failure modes

100% line/branch/function coverage over 123 tests, achieved entirely against `fake-indexeddb`, which is a functional simulator with no resource model. Keyword scan across all 9 test files: **zero** occurrences of `Quota`, `onblocked`, `blocked`, `versionchange`, `onabort`, `structuredClone`, `DataCloneError`, `InvalidState`, `close()`, `bfcache`, `pagehide`, or `keepalive`. The following are therefore unexercised:

1. **Quota exhaustion.** `QuotaExceededError` on `put`, and — the harder case — at **commit** rather than on the request (SEV2 #4 is invisible to the current harness). No test drives the SDK to its own quota ceiling, and no test asserts what happens to the host application's storage when it does.
2. **Private/incognito and IDB-unavailable.** No test opens with `indexedDB === undefined`. `idb.ts:32,110` do `options.indexedDB ?? globalThis.indexedDB`; if the global is absent, `idb.open` throws a `TypeError` at first use rather than degrading. Whether the browser launch survives that is not covered here. Safari's 7-day script-writable-storage eviction and iOS quota behaviour are likewise unmodelled — both would silently delete a dead sibling's pending incident between sessions.
3. **Transaction-commit timing.** `fake-indexeddb` does not reproduce the microtask-drain auto-commit rule, so the SDK's reliance on `request.onsuccess` as a durability point is never challenged.
4. **`versionchange` / blocked upgrade.** No test opens the same database from two connections at different versions, so the absent `onblocked` and `onversionchange` handlers (SEV2 #6) are invisible.
5. **Structured-clone / deserialization failure** of a stored value, and **`getAll`/`getAllKeys` length divergence** — the trigger that makes `values[index] as Uint8Array` (`idb.ts:157,77`) yield `undefined` and detonate SEV1 #1.
6. **Forced connection close** (storage eviction, "clear site data") and the resulting permanent `dbPromise` poisoning.
7. **Real Web Locks semantics under bfcache** — whether a bfcached realm retains its lock. Both outcomes are consequential (see the coexistence section); neither is assertable from a `LockManagerLike` fake.
8. **Real main-thread cost** — the per-record `TextDecoder` allocation and the synchronous `JSON.parse` loop over a full part are never measured, so jank at report assembly is unbounded and unobserved.
9. **The self-capture livelock of SEV1 #2** — no test wires a console-logging `onError` into a failing store, which is why the loop is not caught by an existing regression.

**Test theater assessment: low, with one exception.** The suite avoids the classic traps — persistence is verified by reopening a *fresh* store instance against the same database (`idb.test.ts:40,116`; `idb-chunk-backend.test.ts:362`) rather than by re-reading the writer's own mirror, and the fetch tests assert method, headers, body bytes, and header lowercasing rather than merely that `fetch` was called. The one instance of theater is `coexistence.test.ts:248`, which *asserts the leak of SEV1 #3 as correct behaviour*. Mutation results: **9 of 10 caught** (M1, M2, M5–M11); the single survivor is M3, filed as SEV3 #10. Controls behaved as expected (M1 and M8 failed the exact targeted assertions, not collection errors).

## Checked and found clean

- **Prefix isolation.** `createPrefixedBlobStore` / `createPrefixedKeyedStore` (`instance-coexistence.ts:51-92`) prefix on write and strip on read, and the prefix sits entirely to the left of the inner padded `d/`/`m/` key scheme so inner range scans stay correct. Mutation M11 caught.
- **Prefix range correctness.** `IDBKeyRange.bound(prefix, prefix + '￿')` (`idb.ts:129`) is exact for the fixed-width zero-padded keys actually used (hex instance ids, decimal generations/chunks/sequences). No sibling-prefix bleed.
- **Generation parsing.** `genOfMetaKey` (`idb-chunk-backend.ts:44`) parses by separator, not fixed width, so a >13-digit generation is not truncated — tested at `idb-chunk-backend.test.ts:151,160`.
- **Part-number reuse.** `nextNumber` in `chunk-capture-store.ts:47,50-51` is monotonic and is **not** reset by `clear()`, so a stale data key can never collide with a reused part number.
- **Snapshot pin refcounting** for `removePart`: correct, idempotent `release`, refcounts concurrent snapshots. Mutation M6 caught; REPRO C control confirmed the deferral works.
- **Snapshot freeze boundary.** `i < count && i < records.length` (`:215`) correctly excludes post-snapshot appends and tolerates short reads. Mutation M5 caught.
- **Hydration-vs-live-op ordering.** The `touched` set in both mirrors (`idb-bundle-store.ts:29,41,53`; `idb-report-marker-store.ts:35,54,63`) correctly prevents hydration from re-applying a superseded put **or** resurrecting a removed id. Well tested (4 dedicated tests each).
- **Corrupt marker tolerance.** `idb-report-marker-store.ts:41-47` guards the decode per record and purges the bad entry — i.e. this file gets SEV1 #1 *right*, which makes the chunk backend's omission a local inconsistency rather than a house style.
- **No unhandled rejections escape to the page.** Every async edge is terminated: `blob.put/remove` (`idb-bundle-store.ts:43,54`), marker store (`:56,64`), the write queue (`idb-chunk-backend.ts:95`), `holdSelf` (`web-lock-liveness.ts:58-60`, with an explicit comment about not self-reporting), `recoverIfDead` (`coexistence.ts:194`), and each discovery source (`:154-156`). Verified by reading every call site.
- **Worker portability.** Nothing in the package touches `window`, `document`, or any DOM type. `navigator` is reached defensively (`coexistence.ts:125` `(globalThis as {navigator?…}).navigator?.locks`). `indexedDB`, `IDBKeyRange`, `TextEncoder`/`TextDecoder`, `AbortController`, `fetch`, and `navigator.locks` are all available in Web **and** Service Workers. `@bugsee/webworker`'s bundle-only reuse (`webworker/src/launch.ts:201,324-334`) is sound.
