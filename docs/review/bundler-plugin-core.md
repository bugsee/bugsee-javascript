# Adversarial review — @bugsee/bundler-plugin-core

**Reviewed:** 2026-07-26 · **Scope:** packages/bundler-plugin-core (impl 390 LOC across 5 files, tests 384 LOC across 4 files)
**Verdict:** The security posture of the subprocess layer is genuinely good and better than the brief implies — there is **no `shell: true`, no string-interpolated command line, and the app token is passed via env, never argv**, and a real test asserts the latter. The argv contract was verified against the actual Rust `bugsee-cli` v0.7.2 binary and matches exactly; the debug-ID producer/consumer contract between the CLI and `@bugsee/core` also genuinely agrees. The defects are concentrated not in *how* the process is spawned but in **what happens when it fails**: every `bugsee-cli` failure mode — bad token, missing binary, network error, and (empirically) the plugin's own advertised `dryRun` option — propagates out of `writeBundle` and **aborts the user's build**, with no `errorHandler`/`failOnError` escape hatch and no timeout on a hung child. Three SEV1s follow from that plus one recursive-delete data-loss path. Test quality is the secondary weakness: coverage passes the gate (100% stmt/line/fn, 95.83% branch) but the production spawn path is `/* v8 ignore */`'d wholesale, and 4 of 11 injected mutations survived — including adding `shell: true`, the single most dangerous change possible in this package.

## SEV1

### 1. `dryRun: true` aborts the user's build (empirically exit 11)
- **Where:** `packages/bundler-plugin-core/src/orchestrate.ts:64` (`dryFlag`), applied at `:68` and `:82`; error raised at `packages/bundler-plugin-core/src/run-cli.ts:101-107`
- **What:** `uploadSourcemaps` passes `--dry-run` to **both** commands. `sourcemaps inject --dry-run` by design writes nothing, so the emitted `.map` files still carry no `debug_id`. The immediately following `debug-files upload … --dry-run` then hard-fails because it cannot find a debug-id in any map. `runBugseeCli` converts the non-zero exit into a thrown `BugseeCliError`, which propagates through `runPluginUpload` → `uploadForOutput` → `writeBundle` and fails the build.
- **Why it matters:** `dryRun` is documented at `resolve.ts:23` as "Run bugsee-cli with `--dry-run` (no upload, no deletion)" — i.e. the *safe* diagnostic. It is the option a user reaches for to verify their config without side effects, and it is exactly the option that breaks their build. It fails on **every freshly-built output directory**, which is the only kind a bundler ever produces; it would only pass on a dir where a previous non-dry-run inject had already stamped the maps.
- **Evidence:** Ran the real binary (`packages/bundler-plugin-core/node_modules/.bin/bugsee-cli`, v0.7.2) with the exact argv the plugin constructs, on a fresh dist dir:
  - `bugsee-cli sourcemaps inject <dir> --dry-run` → exit **0**
  - `bugsee-cli debug-files upload <dir> --type sourcemaps --version 1.0.0 --build 7 --dry-run` → exit **11**, stderr: `error: input invalid: source map has no debug_id/debugId/uuid: … — run 'bugsee-cli sourcemaps inject <bundle-dir>' first to embed one`

### 2. Any `bugsee-cli` failure breaks the user's build; there is no opt-out, and a missing binary surfaces as a raw ENOENT
- **Where:** `packages/bundler-plugin-core/src/plugin.ts:38-43` and `:52-57`; `packages/bundler-plugin-core/src/resolve.ts:58-76`; `packages/bundler-plugin-core/src/orchestrate.ts:68,71`; `packages/bundler-plugin-core/src/run-cli.ts:78,101-107`
- **What:** There is **no `try`/`catch` anywhere in `src/`** and no failure-policy option on `BugseePluginOptions` (`resolve.ts:12-27` exposes only `appToken`/`appVersion`/`appBuild`/`endpoint`/`deleteMaps`/`dryRun`/`disabled`). Every failure — expired/invalid token, transient network error, server 5xx, binary not on PATH — rejects `writeBundle` and aborts the build. For a missing binary the rejection is not even a `BugseeCliError`: `run-cli.ts:78` forwards Node's raw spawn error unchanged.
- **Why it matters:** A telemetry-upload side effect must not be able to fail a production deploy. This inverts the normal contract for this class of plugin (`@sentry/webpack-plugin` ships `errorHandler` precisely for this) and means a Bugsee outage or a rotated token turns into a broken CI pipeline for every customer using the plugin. It also directly contradicts design decision **D5** in `docs/design/source-maps.md` §5, which promises "a clear error if unresolved" — `resolveBugseeCli` (`run-cli.ts:54-60`) performs no existence check and emits no guidance.
- **Evidence:** Drove the real `writeBundle` hook via `bugseeUnpluginFactory({appToken:'tok'})` against a stub CLI exiting 20 — the returned promise **rejected** (assertion `expect(err).toBeDefined()` passed). Separately, `runBugseeCli(['sourcemaps','inject','.'], {resolveBinary: () => 'definitely-not-installed-bugsee-cli'})` rejected with exactly `{ name: 'Error', code: 'ENOENT', message: 'spawn definitely-not-installed-bugsee-cli ENOENT', isBugseeCliError: false }`. Confirmed no escape hatch by grepping `errorHandler|failOnError|silent|throwOn|catch` across `src/*.ts` → no matches outside tests.

### 3. A relative `output.file` resolves the output dir to `"."`, then every `*.map` under the CWD is recursively unlinked — including `node_modules/` and `src/`
- **Where:** `packages/bundler-plugin-core/src/plugin.ts:21` (`return dirname(output.file)`); deletion at `packages/bundler-plugin-core/src/orchestrate.ts:39-52`, invoked at `:90`
- **What:** `resolveOutputDir({ file: 'bundle.js' })` returns `'.'` because `path.dirname('bundle.js') === '.'`. That value becomes `outDir`, which is handed to `defaultDeleteMapFiles`, which walks the tree **recursively with no depth limit, no `node_modules` exclusion, and no restriction to build artifacts**, unlinking every entry whose name ends in `.map`.
- **Why it matters:** Silent, unrecoverable data loss in the user's working tree — authored `.map` files under `src/`, and dependency source maps under `node_modules/` (breaking debugging until a reinstall). A relative `output.file` is a completely ordinary Rollup library config, and `bugseeRollupPlugin` is an advertised export (`plugin.ts:70`, re-exported at `index.ts:13`). Deletion is on by default (`resolve.ts:52`, `orchestrate.ts:63`).
- **Evidence:** `node -e "path.dirname('bundle.js')"` → `"."`. Then ran `defaultDeleteMapFiles` against a temp tree containing `node_modules/left-pad/index.js.map`, `src/authored.ts.map`, `bundle.js.map`, `sitemap.map.js`: it deleted **3** files including the `node_modules` and `src` maps (assertion `expect(deleted.length).toBe(3)` passed).

## SEV2

### 4. No timeout on the spawned process — a hung `bugsee-cli` hangs the build indefinitely
- **Where:** `packages/bundler-plugin-core/src/run-cli.ts:63-80` (`defaultSpawn`); `RunBugseeCliOptions` at `:20-33` has no timeout field
- **What:** The promise settles only on the child's `close` or `error` event. No `timeout`/`AbortSignal` is passed to `nodeSpawn`, and no watchdog exists at any layer. A `bugsee-cli` blocked on a hanging TCP connect to the endpoint (a plausible CI failure mode against a firewalled/proxied network) leaves `writeBundle` pending forever.
- **Why it matters:** A wedged build hangs until the CI job's global timeout, burning a full runner slot and producing no diagnostic. Uploads are network I/O against a user-supplied `endpoint`, so this is reachable purely through misconfiguration.
- **Evidence:** Raced `runBugseeCli(['x'], {resolveBinary: () => <script sleeping 2.5s>})` against a 1.2s timer; the timer won (`expect(raced).toBe('STILL-RUNNING-AFTER-1.2s')` passed), confirming nothing in the SDK bounds the wait. Code read confirms no timeout option exists to set.

### 5. Binary resolution is a bare PATH lookup with no preflight check; the "zero-config" claim does not hold under pnpm, and `.cmd` shims are unreachable on Windows
- **Where:** `packages/bundler-plugin-core/src/run-cli.ts:47-60` (resolver + its doc comment), `:65-69` (spawn call, no `shell`)
- **What:** When `BUGSEE_CLI_PATH` is unset the resolver returns the bare string `'bugsee-cli'` and relies on PATH. The doc comment at `:49-51` asserts the binary "is present with no extra install (zero-config)" because `@bugsee/bugsee-cli` is a direct dependency. Two verified gaps: (a) under pnpm's default isolated layout a **transitive** dependency's bin is not linked into the consuming project's `node_modules/.bin`, so a user installing `@bugsee/vite-plugin` does not get `bugsee-cli` on the PATH their build sees; (b) `node_modules/.bin/bugsee-cli` is a POSIX `sh` shim — on Windows npm/pnpm generate a `.cmd`/`.ps1` counterpart, which Node's `spawn` cannot execute without `shell: true`.
- **Why it matters:** The failure lands as the raw `ENOENT` from finding #2 — an opaque `spawn bugsee-cli ENOENT` that breaks the build with no hint about installing or setting `BUGSEE_CLI_PATH`. Combined with #2 (no error handling), a resolution miss is a hard build failure rather than a skipped upload.
- **Evidence:** In this very workspace, `ls node_modules/.bin/ | grep bugsee` at the repo root returns **nothing**, while `packages/bundler-plugin-core/node_modules/.bin/bugsee-cli` exists — i.e. pnpm scoped the bin to the declaring package only. `file` on that shim reports `POSIX shell script text executable`. Code read confirms no `shell` option and no `existsSync`/preflight anywhere. *(The Windows half of this is inferred from documented Node `spawn` behavior — I could not execute it on this darwin host, and I flag it as such.)*

### 6. No re-entrancy or concurrency guard around the hook — overlapping runs can delete maps out from under a concurrent inject
- **Where:** `packages/bundler-plugin-core/src/plugin.ts:38-43` (shared closure, no in-flight tracking), `:48-49` (vite/rollup), `:52-57` (webpack)
- **What:** `uploadForOutput` holds no in-flight promise, no per-dir lock, and no already-processed set. Rollup/Vite invoke `writeBundle` **once per output**, and a multi-output config whose entries resolve to the same directory (e.g. `output: [{ dir: 'dist' }, { file: 'dist/legacy.js' }]` — both resolve to `dist`) produces two concurrent pipelines over one tree: one may be running step 3 (`defaultDeleteMapFiles`, `orchestrate.ts:90`) while the other is still in step 1/2 reading those maps. `vite build --watch` additionally re-runs the whole inject→upload→delete pipeline on every rebuild.
- **Why it matters:** In the overlapping-dir case the loser's upload can see maps that were just unlinked, producing a spurious hard build failure (per #2) or a silently incomplete symbol upload. In watch mode it means two extra subprocess spawns per keystroke-triggered rebuild.
- **Evidence:** Code read of `plugin.ts:32-61` — the factory computes `resolved` once and returns hooks that share no state; there is no `apply: 'build'` guard and no dedupe. Server-side dedupe (`16004`-idempotent, per `docs/design/source-maps.md` §2) limits the *upload* damage, but not the local delete/read race.

## SEV3

### 7. Four mutations survived the test suite, including `shell: true`
- **Where:** `packages/bundler-plugin-core/src/run-cli.ts:65-69`, `:101`; `packages/bundler-plugin-core/src/orchestrate.ts:46`; `packages/bundler-plugin-core/src/plugin.ts:41`
- **What:** Ran 11 mutations; **all 4 control mutations were caught** (wrong `--type` value, token leaked onto argv, `dirname` dropped, `!dryRun` guard dropped), proving the harness is valid. Survivors:
  - **H2 — adding `shell: true` to `defaultSpawn` survives.** The most security-critical property of this package is asserted by nothing.
  - **H4 — replacing `await runPluginUpload(...)` with `void runPluginUpload(...)` survives.** A dangling-promise regression (silently dropped uploads + unhandled rejection) would ship green. This is possible because `plugin.test.ts` only ever constructs with `disabled: true` (`plugin.test.ts:42,50,72`), so the enabled path is never exercised in unit tests.
  - **H1 — `entry.name.endsWith('.map')` → `.includes('.map')` survives.** Fixtures (`orchestrate.test.ts:103-108`) can't distinguish the two; the mutant would additionally delete a file named e.g. `sitemap.map.js`.
  - **H3 — `result.code !== 0` → `result.code > 0` survives** (low real-world impact: `code ?? 0` at `run-cli.ts:79` means the value is never negative).
- **Why it matters:** Binding standard is a per-entity mutator loop; these four are exactly the entities where a silent regression is most expensive.
- **Evidence:** Scripted mutate → `pnpm exec vitest run` → restore-from-backup, for each mutation. Controls 4/4 caught, hunts 4/7 survived. All files restored; `git status --short` empty.

### 8. The production subprocess path is excluded from the coverage gate
- **Where:** `packages/bundler-plugin-core/src/run-cli.ts:62` / `:81` (`/* v8 ignore start|stop */` around all of `defaultSpawn`); `packages/bundler-plugin-core/src/plugin.ts:50` / `:59` (same around the webpack `afterEmit` glue)
- **What:** `docs/implementation-standards.md` §4 permits `/* v8 ignore */` only for "unreachable or platform-guarded code". `defaultSpawn` is neither — it is the real, always-taken production spawn path on every runtime. Excluding it is what lets findings #4 (no timeout) and #7/H2 (`shell: true`) sit invisible to the 100% gate. Only 68 statements are measured across a 390-LOC package.
- **Evidence:** `vitest run --coverage` → 100% stmt/line/fn, 95.83% branch, 68/68 statements; the text report lists only `orchestrate.ts` and `resolve.ts` as having any uncovered branches. One test (`run-cli.test.ts:79-84`) does exercise `defaultSpawn` via `process.execPath --version`, so the annotation also understates real coverage.

### 9. Both wrapper READMEs are stale and describe a feature that does not exist
- **Where:** `packages/vite-plugin/README.md`, `packages/webpack-plugin/README.md`
- **What:** Both read "Vite/Webpack plugin: auto-define `__BUGSEE_DEBUG__`, source-map upload trigger" and "**Status: stub.** Tier 4 (design §5)." The packages are built and shipped, and neither defines `__BUGSEE_DEBUG__` (grep finds no such symbol in either `src/`).
- **Why it matters:** These are the public-facing docs for the two packages users actually install; they claim the package is a stub.

### 10. Design-doc drift on the `@bugsee/bugsee-cli` dependency kind
- **Where:** `packages/bundler-plugin-core/package.json` (`dependencies`) vs `docs/design/source-maps.md` §4
- **What:** The design doc calls `@bugsee/bugsee-cli` "an **optional** dependency"; `package.json` declares it a hard `dependencies` entry (`^0.7.2`), and `run-cli.ts:50` correctly documents it as a "DIRECT dependency". Code and package.json agree with each other; the design doc is the outlier. As a hard dep it forces the platform-binary download on every install of any consumer, with `BUGSEE_CLI_PATH` as the only escape — which is a deliberate trade-off worth stating accurately in the doc.

### 11. `.map` deletion is broader than "client source maps"
- **Where:** `packages/bundler-plugin-core/src/orchestrate.ts:46`
- **What:** The suffix test matches **any** `*.map`, so a Vite build's `assets/style.css.map` is deleted alongside the JS maps, even though only JS maps were uploaded. Defensible under the privacy rationale (`:22`, `:87`) but undocumented — `resolve.ts:21` says only "Delete client `.map`s after upload".

## Checked and found clean

- **No shell injection surface.** `nodeSpawn(command, args, …)` (`run-cli.ts:65`) passes an argv **array** with no `shell` option and no string concatenation anywhere. No user-controlled value (token, endpoint, version, build, outDir) is ever interpolated into a command string. `resolveBugseeCli` returning an unvalidated `BUGSEE_CLI_PATH` (`run-cli.ts:54-58`) is not an injection vector without a shell — and that env var is already the user's own trusted input.
- **Secrets stay out of `ps`.** Token and endpoint go into the child env (`run-cli.ts:92-98`), never argv, and `run-cli.test.ts:45` asserts `expect(calls[0]?.args).not.toContain('secret-tok')`. My control mutation CTRL-B (appending the token to argv) was **caught** by that assertion — a genuinely load-bearing security test, mirrored in `packages/instrumentation-tests/test/sourcemaps.e2e.ts`. `BugseeCliError.message` (`run-cli.ts:103`) interpolates only argv, so it cannot leak the token; the carried `stderr` could in principle relay a token the CLI echoed, but I found no evidence the Rust CLI ever prints the token value.
- **The argv contract matches the real binary exactly.** Verified against `bugsee-cli` v0.7.2 by running `--help`: `debug-files upload [OPTIONS] --version <VERSION> --build <BUILD> <PATHS>...` with `--type` accepting a `sourcemaps` variant, and `--app-token` / `--endpoint` declared `global = true` with `env = "BUGSEE_APP_TOKEN"` / `env = "BUGSEE_ENDPOINT"` (`bugsee-cli/src/cli/mod.rs:32,40`). `sourcemaps inject <PATHS>... [--dry-run]` confirmed at `bugsee-cli/src/cli/sourcemaps.rs`. Both non-dry-run invocations exited 0 against a real fixture. The brief's claims about spawning the Rust CLI and not reimplementing upload are accurate.
- **Producer and consumer of `_bugseeDebugIds` genuinely agree.** The CLI emits `…e._bugseeDebugIds=e._bugseeDebugIds||{},e._bugseeDebugIds[n]="<uuid>"` where `n=(new e.Error).stack`, plus `//# debugId=<uuid>` and `"debug_id":"<uuid>"` in the `.map`. `packages/core/src/debug-id.ts:18` reads that map and `:29-38` keys it by `parseStack(stack)[0]?.file` — the top frame of the registration stack is the bundle's own URL, which is what `attachDebugIds` (`:41-49`) then matches against captured frames. Verified by observing the actual injected bytes.
- **Debug IDs are deterministic across rebuilds.** Injecting identical content twice produced the identical UUIDv5 (`6e0decd3-3747-5777-a4e1-c3f3c318635a` both runs), so rebuilds are idempotent and re-uploads dedupe. Generation lives entirely in the Rust CLI — this package contains no debug-ID logic, so the brief's "verify how debug IDs are generated/injected" applies to `bugsee-cli`, not here.
- **Async hooks are correctly awaited — no dangling promises in the shipped code.** `plugin.ts:48-49` return the promise from `uploadForOutput`; `plugin.ts:52` uses webpack's `tapPromise` and returns the inner promise; `orchestrate.ts:68,71,90` and `resolve.ts:67` all await. (Nothing *enforces* this — see #7/H4.)
- **Maps are not deleted when the upload fails.** Deletion (`orchestrate.ts:88-91`) is sequenced strictly after both `run` calls, so a throw from either aborts before any unlink — the user keeps their maps on a failed upload. `orchestrate.test.ts:62` asserts the ordering (`['sourcemaps','debug-files','delete']`).
- **No temp files.** The package writes nothing of its own; packing/temp handling is entirely inside the Rust CLI, so there is no cleanup path to leak.
- **Option resolution is correct and well covered.** Precedence (explicit > env > default), the `enabled` gate requiring a non-empty token, and the `disabled` override are each asserted (`resolve.test.ts:5-56`); `runPluginUpload` no-ops when disabled (`resolve.ts:63-65`, asserted at `resolve.test.ts:87-96`). A missing token makes the plugin a silent no-op rather than an error — correct, and it means the SEV1 build-break paths are only reachable once a user has configured a token.
- **Export surface is coherent and fully consumed.** Every symbol in `index.ts:4-34` type-checks and resolves; `@bugsee/vite-plugin` uses `bugseeUnplugin.vite` and `@bugsee/webpack-plugin` uses `bugseeUnplugin.webpack`, both re-exporting `BugseePluginOptions`. No meta-framework adapter (nextjs/nuxt/sveltekit/astro/remix) wires the bundler plugin at all — grep found references only in `packages/instrumentation-tests`, so there is no adapter contract drift to report.
- **Gates pass.** `tsc --noEmit` clean (rc=0); `vitest run` 34/34 passing; coverage 100% line/fn/stmt and 95.83% branch, above the ≥90% branch gate.
- **Working tree untouched.** `git status --short packages/bundler-plugin-core packages/vite-plugin packages/webpack-plugin` is **empty** after all mutation and verification work; every mutated file was restored from a scratchpad backup (never via git).
