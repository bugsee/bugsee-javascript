# Node.js capture-API research

Scope: `node:*` core APIs only (browser/DOM and framework-adapter APIs are other researchers' subjects).
Cross-checked against the SDK's actual Node capture code (`packages/node/src/*.ts`) so nothing here
duplicates what is already built: outbound HTTP is captured by monkey-patching `http.request`/`http.get`
(`packages/node/src/http-interceptor.ts`); inbound HTTP by monkey-patching `http.Server.prototype.emit` /
`https.Server.prototype.emit` (`packages/node/src/http-server-interceptor.ts`); memory/CPU/event-loop
metrics by a periodic sampler built on `process.memoryUsage`/`process.cpuUsage`/`os.*`/
`perf_hooks.monitorEventLoopDelay` (`packages/node/src/system-metrics.ts`); CPU profiling by a
`node:inspector` `Profiler` session (`packages/node/src/cpu-profiler.ts`); ANR/hang detection by a custom
`worker_threads` + `SharedArrayBuffer` heartbeat, not by any async/event-loop introspection API
(`packages/node/src/event-loop-watchdog.ts`). None of the below re-proposes those paths as net-new; several
propose *replacing* their mechanism while keeping their data contract.

Node version used for verification: docs and doc-diffs were pulled from `nodejs.org/api` (current/latest),
cross-checked against the versioned snapshots `nodejs.org/dist/latest-v18.x`, `latest-v20.x`, and
`latest-v22.x` to determine what actually exists on the SDK's declared `engines: node >= 18` floor — the
per-channel "Added in" version is frequently *not* printed in the current docs page, so several rows below
are gated by doc-diffing three version snapshots rather than a quoted version string; those are marked
accordingly in Confidence.

## Top 5 recommendations

1. **`diagnostics_channel` HTTP client/server channels as a replacement capture mechanism for outbound AND
   inbound HTTP.** The core set (`http.client.request.start`, `http.client.response.finish`,
   `http.server.request.start`, `http.server.response.finish`, plus `net.client.socket`/`net.server.socket`)
   exists unchanged back to Node 18.20.8 — verified by diffing the v18/v20/v22 doc snapshots. Node
   *publishes the live `ClientRequest`/`IncomingMessage`/`ServerResponse`/`net.Socket` objects itself* at
   well-defined lifecycle points. That is a straight upgrade over the current approach: no `require('http')`
   monkey-patch to keep in sync with Node's internal call shape, official support surface, and it comes with
   the socket object attached so connection reuse / keep-alive can be observed for free. Net-new on top: the
   HTTP/2 channel family (`http2.client.stream.*` / `http2.server.stream.*`), which the SDK currently
   captures **not at all** (the interceptor only patches `http`/`https`, not `http2`), including
   `timeToFirstByte`/`timeToFirstHeader` fields HTTP/1 never gives you.
2. **`net` connection-attempt events + TLS socket introspection** to enrich network spans with what actually
   failed or was slow at the transport layer — `connectionAttempt`/`connectionAttemptFailed`/
   `connectionAttemptTimeout` (dual-stack Happy-Eyeballs attempts, Node ≥20.12/21.6) and
   `tlsSocket.isSessionReused()`/`getProtocol()`/`getCipher()` (session-resumption and handshake detail,
   Node ≥0.11.4 — old and safe). Today a slow or failing outbound call just looks like "the request took
   900ms" or "ECONNRESET"; these give the support engineer "attempted 2001:...:1 (IPv6) first, it timed out
   at 250ms, fell back to IPv4" or "TLS session was NOT reused, full handshake every request."
3. **`perf_hooks` `'gc'` entries via `PerformanceObserver`.** The SDK has zero GC-specific telemetry today —
   `traces.system` samples heap/RSS periodically but a GC pause between samples is invisible. This is a
   discrete, cheap (no documented overhead caveat, unlike `'http'` entries — see below), always-on-when-
   observed event with `startTime`/`duration`/`kind` (major/minor/incremental) that turns "the event loop
   stalled for 40ms" into an explicit `gc.pause` span/metric, correlatable against the existing
   ANR/hang-detection and event-loop-lag samples.
4. **`worker_threads` per-worker resource attribution** — `worker.performance.eventLoopUtilization()`,
   `worker.resourceLimits`, `worker.cpuUsage()`, `worker.getHeapStatistics()`. The SDK's own multi-instance
   coexistence design already runs across `worker_threads`, and Node app authors commonly offload CPU work
   to worker pools; today the SDK has no way to say "which worker actually consumed the CPU/heap" — this is
   the only sanctioned way in Node to get resource numbers scoped to one worker from outside it.
5. **`v8.getHeapStatistics()` / `getHeapSpaceStatistics()`** as a free enrichment of the existing periodic
   system-metrics sampler. Both are documented negligible-overhead, synchronous, and give old-space/
   new-space/code-space breakdown and `heap_size_limit`/`number_of_native_contexts` that `process.memoryUsage()`
   doesn't — the difference between "heap usage crept up" and "you're about to hit `heap_size_limit`" or
   "you're leaking native contexts (a classic closures-over-`vm.Context` leak)."

## Interesting, but not recommended

- **`async_hooks.createHook()` (raw lifecycle hooks).** This is the API that would, in theory, give a complete
  causal graph of every async operation in the process — genuinely the richest signal available. Not
  recommended because: (1) Node's own docs say, verbatim, to migrate away from it and call out "usability
  issues, safety risks, and performance implications"; (2) it is process-global — enabling it for the SDK's
  own purposes forces Promise `asyncId` tracking for *every* promise in the app, a side effect the SDK
  cannot scope to itself; (3) the `destroy` hook specifically has documented additional GC-tracking overhead;
  (4) a throwing hook callback kills the process outside the normal `uncaughtException` path. `AsyncLocalStorage`
  (already used) gets the SDK's actual need — context propagation — without any of this.
- **`trace_events`.** Tempting because the category list (`node.http`, `node.fs.*`, `node.dns.native`,
  `node.net.native`, `v8`) reads like exactly what this research is looking for. Not recommended as a live
  capture mechanism because it is fundamentally a *file* format (`node_trace.*.log`, meant for
  `chrome://tracing`), not an in-process event stream — there is no documented way to receive trace events
  as live JS objects for building spans on the fly. It would mean writing files to disk and re-parsing them,
  which the SDK's disk-capture pipeline could technically do, but at that point `diagnostics_channel` already
  gives the same underlying data (http/net/dns/module) as live objects for less complexity. Also explicitly
  unavailable in Worker threads.
- **`inspector.Network.*`.** Included above mainly as a warning: the name strongly suggests "subscribe to
  Node's network activity," but it is the opposite — a *publish* surface for reporting activity you already
  captured elsewhere into an attached DevTools/CDP client. Anyone skimming the API list for network
  telemetry will be tempted to reach for this; it does not do what the name implies.
- **`v8.writeHeapSnapshot()` / `getHeapSnapshot()` / `inspector`'s `HeapProfiler.takeHeapSnapshot`.** Real,
  valuable data — but both documented as blocking the event loop and requiring ~2x the current heap size in
  memory, with the resulting snapshot containing essentially every live object/string in the process (auth
  tokens, request bodies, session data, all of it). Fine as a manual, opt-in, report-time diagnostic a
  developer explicitly triggers; wrong shape for anything sampled or default-on.
- **`tlsSocket.on('keylog')`.** Directly yields TLS session key material. Never appropriate for a production
  SDK to touch, full stop — included only because it showed up while researching TLS diagnostics and is
  worth an explicit "do not do this" rather than a silent omission.
- **`module.register()` loader hooks for module-load timing.** Structurally mistimed for this SDK: to see a
  module's resolve/load timing you must register the hook *before* that module is imported, which for a
  synchronous `require()`-based or already-imported ESM graph means before the app's own entry point runs —
  earlier than `launch()` can plausibly hook in for most integration patterns. Only dynamic `import()`s that
  happen after `launch()` would be visible, which is a narrow slice of "module loading" in most apps.
- **`process.execve` diagnostics_channel.** Real channel, real data (`execPath`/`args`/`env`) — but `execve`
  (POSIX process-image replacement, distinct from `child_process.spawn`) is a niche, rarely-invoked API in
  typical Node server/CLI code, and the payload includes the full environment being exec'd into. Narrow
  applicability plus high sensitivity for a payload that's almost never emitted in practice.
