# Browser built-in APIs — capture research

Researcher: browser built-in APIs (PerformanceObserver family, Reporting API, memory/device,
Streams, storage, scheduling, page lifecycle, errors). Primary source: MDN, cross-checked against
recent (late-2025/2026) compat changes via web search where MDN's rendered compat tables weren't
directly fetchable. Every "documented"/"unverified" tag below reflects an honest confidence
assessment, not a formality — several rows here turned up genuinely surprising, very recent (Dec
2025–Mar 2026) Safari/Firefox compat shifts that are worth independently re-checking on caniuse.com
before anyone builds on them.

## Top 5 recommendations

1. **`PerformanceResourceTiming.serverTiming` (row 8).** This isn't a speculative find — the SDK's
   own code already names the gap. `packages/performance/src/http-spans.ts:65` documents that
   cross-origin `Server-Timing: traceparent;desc="…"` propagation (the BE→FE trace-continuation
   return path, X3b/F3b) is only readable cross-origin via `PerformanceResourceTiming.serverTiming`
   + `Timing-Allow-Origin`, and calls it "the deferred passive F3b path." The backend already sends
   this header (`packages/node/src/server-instrument.ts`); the browser side of the loop is unbuilt.
   `serverTiming` itself has been Baseline-widely-available since March 2023 — no browser gap, only
   an implementation gap.
2. **`securitypolicyviolation` (`SecurityPolicyViolationEvent`, row 16).** Zero browser caveats —
   Baseline widely available since October 2018, all four engines, no header/permission/isolation
   needed, just a `document.addEventListener`. Not currently captured. "A script from evil.example
   was blocked by your CSP" is exactly the class of externally-caused incident a support engineer
   wants without asking the customer to dig through a separate CSP dashboard.
3. **`layout-shift` raw entries + `largest-contentful-paint` raw entries (rows 4–5).** The SDK
   already reports the finalized CLS/LCP *numbers*; it discards the *attribution* — which DOM node
   shifted, which element was the LCP candidate, its `url`/`size`. Attaching `sources[].node` (via
   the same masking discipline as `describeTarget`) and `element`/`url`/`size` turns "CLS regressed
   to 0.31" into "your `.ad-slot` div shifted 120px when a late ad loaded" — the difference between
   a metric and an actionable finding. LCP just crossed into 4-engine Baseline support in December
   2025 (Safari 26.2), so this is now broadly meaningful, not Chromium-only trivia.
4. **`long-animation-frame` (LoAF, row 1).** Chromium-only (Chrome/Edge 123+, no Firefox commitment,
   no Safari), but where it's present it is strictly richer than the `longtask` span the SDK already
   builds: per-script attribution (`sourceURL`, `sourceFunctionName`, `invoker`, per-script
   `duration`) turns "something blocked the main thread for 340ms" into "a `setTimeout` callback
   from `analytics-bundle.js:41203` blocked it." High debugging value where available; treat as a
   Chromium-only bonus layer alongside the existing cross-engine `longtask` span, never a
   replacement for it.
5. **`navigator.storage.estimate()` (row 22).** Broadly supported (Baseline since September 2023,
   secure-context only, no other gate) and directly relevant to the SDK's own architecture: the
   browser tier persists its bundle/capture store in IndexedDB against the same origin quota it
   would be measuring. A slow, session-scoped sample answers "is the SDK's own local buffer close
   to the origin's storage ceiling" and "is the app's *own* IndexedDB usage why uploads are
   stalling" — a self-diagnostic with no real cost or caveat.

Runner-up worth flagging even though it didn't make the top 5: the Reporting API's **`crash`**
report type (row 15) is the one mechanism that can report a renderer OOM/hang *after JS itself is
dead* — architecturally the closest browser-native analogue to the Electron `crashReporter`
minidump harvest already built for the desktop tier. It's Chromium-only, still WICG-stage, and
needs new server-side ingest (a `Reporting-Endpoints` header + a collector endpoint), so it's a
bigger lift than anything else here — but given "the SDK cares about crashes" is an explicit
priority, it deserves a design spike, not a dismissal.

## What requires cross-origin isolation or a permission (what most sites can't use)

- **`performance.measureUserAgentSpecificMemory()`** — secure context **+** COOP+CROSS-ORIGIN-EMBEDDER-POLICY cross-origin isolation. This is the hardest constraint in the whole document: any third-party ad, widget, analytics tag, or unopted-in iframe embed on the page breaks isolation for the ENTIRE page, not just that embed. Real-world customer sites with any third-party surface area typically cannot enable this. Treat as opt-in-only, gated on `self.crossOriginIsolated`, never a default.
- **`navigator.storage.estimate()`** — secure context (HTTPS/localhost) only; no isolation or permission beyond that. The one storage/memory-adjacent API here that's actually broadly usable.
- **`getHighEntropyValues()`** on `NavigatorUAData` — no explicit user-facing permission prompt for a same-origin top-level call in Chromium today, but some high-entropy hints are Permissions-Policy-gatable for cross-origin iframe delegation, and the whole surface is Chromium-only regardless — flagged `unverified` on the exact gating behavior in this document; the low-entropy `.platform` (already used) needs nothing.
- **`navigator.getBattery()`** — no explicit permission prompt where implemented (Chromium/older Firefox), but Safari has never implemented it at all, on fingerprinting grounds — already the SDK's reality today, unchanged.
- **`window.crashReport`/Reporting-API `crash` type** — no browser-side permission, but requires the SITE OPERATOR to configure a `Reporting-Endpoints` header pointing at a real collector — an infrastructure prerequisite, not a runtime permission, but a hard gate nonetheless (nothing is delivered without it).
- **`elementtiming` (Element Timing)** — no permission, but requires the CUSTOMER to annotate their own markup per element — an opt-in cost on the integrator's side, not the end user's.
- **Soft Navigation Heuristics** — gated behind a Chrome origin-trial token (or a local `chrome://flags` toggle) — not deployable to arbitrary end users' browsers at all today, regardless of permission model.

## What I would NOT recommend, and why

- **Soft-navigation heuristics.** Single-browser (Chrome only), still in its "final" origin trial as of March 2026, and the SDK's own Navigation-API-based `navigation-source.ts` already solves the SPA route-detection problem this targets, without a trial token. Revisit once/if it ships stable and un-flagged everywhere.
- **`SharedWorker` as a capture-buffer redesign.** The complete absence of SharedWorker on Chrome for Android — the single largest mobile browser by share — makes it a non-starter as a PRIMARY mechanism for anything session-critical. The existing IndexedDB + Web Locks coexistence design already solves cross-tab coordination without this gap.
- **`layout-shift`/LCP-element/Element-Timing DOM-node capture without reusing the existing masking discipline.** All three hand back live `Element` references. Wiring them up as a quick "just log `entry.sources[0].node.outerHTML`" would be a straightforward way to leak masked/sensitive DOM content that the rest of the SDK goes to real lengths (`SENSITIVE_INPUT_MATCHERS`, `describeTarget`, replay blackout) to protect. Any implementation MUST route through the existing single definition of "sensitive field," not restate it — flagging this explicitly since the CLAUDE.md project rule calls out exactly this failure mode ("three copies once drifted apart and a card field went unmasked").
- **Treating `performance.memory` deprecation as an action item.** MDN calls it deprecated and non-standard, but its replacement's cross-origin-isolation requirement makes it non-viable as a wholesale swap for the vast majority of real sites. Keep the current trace; add `measureUserAgentSpecificMemory` as a narrow, clearly-gated opt-in, not a migration.
- **`scheduler.postTask`/`isInputPending`/`requestIdleCallback` as "capture APIs."** They're genuinely useful, but for making the SDK's OWN background work (flush, sampling, serialization) less disruptive to the host app — not for producing telemetry. Including them here because the brief asked, but they belong in an implementation-quality backlog, not a capture-stream backlog.
- **Building on any row marked `unverified` in this document without an independent re-check.** Several compat claims here (ReportingObserver's Firefox/Safari rows, the Navigation API's "Baseline 2026" badge, `first-paint`'s non-Chromium floor) came from web-search summaries of caniuse/MDN rather than a directly-rendered compat table, and a couple read as surprisingly recent/generous relative to these APIs' historical Chromium-only reputations. Re-confirm on caniuse.com directly before any of them drive a build decision.
